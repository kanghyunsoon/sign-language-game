# 게임 프론트엔드 작업 기록

모델의 예측을 게임 입력으로 연결하고, 중복 입력과 대전 중 보드 상태가 어긋나는 문제를 수정했습니다. 게임 선택 이후 화면과 인식 결과 처리, 한글 블록 쌓기와 대전을 맡았습니다. 구현에는 AI의 도움을 받았으며, 아래는 실행하면서 확인하고 수정한 내용입니다.

[프로젝트 소개로 돌아가기](../README.md) · [당시 트러블슈팅 기록](../frontend/src/game/docs/game-troubleshooting.md)

## 1. 손 모양 하나에 블록이 여러 번 생겼습니다

같은 자모가 여러 프레임 연속으로 예측되면 매번 입력으로 처리될 수 있었습니다. 예측 결과와 입력 확정을 나누고, 한 번 확정한 뒤에는 손 모양을 풀거나 다음 입력 조건을 만족해야 다시 입력되도록 했습니다.

| 설정 | 후보를 모으는 조건 | 유지 시간 | 사용 위치 |
| --- | --- | ---: | --- |
| 기본 | 4프레임 중 2표 | 100ms | 기본 인식 세션·개발 화면 |
| 반응형 | 2프레임 중 1표 | 35ms | 솔로·대전·봇 연습 화면 |

이 값은 확정 조건입니다. 35ms 안에 카메라 촬영부터 블록 생성까지 끝난다는 뜻은 아닙니다. 모드별 설정은 [시간축 디코더](../frontend/src/game/recognition/temporal)에서 확인할 수 있습니다.

## 2. 이미 지난 손 모양이 뒤늦게 입력됐습니다

응답을 기다리는 동안 촬영 프레임이 계속 쌓이면 손을 바꾼 뒤에도 이전 예측이 도착할 수 있었습니다. 다음 요청으로 보낼 프레임은 최신 1개로 덮어쓰고, 처리 중인 요청이 끝나면 그 프레임을 사용하도록 했습니다.

응답을 받을 때도 세션과 요청 순서를 확인해 이미 지난 응답을 제외했습니다. 프레임 나이를 검사하는 기준 시점은 랜드마크 추출이 끝난 때이므로, 이 검사값을 촬영부터 계산한 전체 지연으로 설명하지 않았습니다.

## 3. 화면 이동과 영상 연결이 카메라 수명에 영향을 줬습니다

게임 인식, 미리보기와 대전 영상이 카메라를 함께 사용했습니다. 한 화면이 정리되면서 다른 기능이 쓰던 카메라까지 종료되거나 시작 요청이 겹치는 문제가 있었습니다.

카메라 시작 요청을 공유하고, 각 화면에서 카메라를 직접 종료하지 않도록 사용·정리 흐름을 나눴습니다. AI 서버에는 손 랜드마크를 보내고, 대전 영상은 WebRTC로 상대방과 주고받습니다. 따라서 서비스 전체가 영상을 전송하지 않는 구조는 아닙니다.

## 4. 한글 모양과 블록의 충돌 영역이 달랐습니다

글자를 사각형 하나로 처리하면 획 사이의 빈 공간에서도 충돌했습니다. 자모별 충돌 조각을 사용해 한글 모양에 맞춰 블록을 쌓도록 했습니다.

게임은 저장된 자모별 충돌 좌표를 우선 사용합니다. 글자를 캔버스에 그려 알파 값을 읽는 방식은 충돌 좌표를 만들고 확인하는 도구와 대체 경로에도 쓰입니다. 모든 블록이 생성될 때마다 글자를 다시 분석하는 구조는 아닙니다.

## 5. 두 사람이 같은 목표를 거의 동시에 맞혔습니다

양쪽 브라우저가 각자 입력을 확정하면 하나의 공통 목표에서 두 블록이 생길 수 있었습니다. 입력을 바로 보드에 반영하지 않고 호스트에게 요청하게 했습니다. 호스트는 먼저 도착한 유효 요청을 승인하고, 양쪽은 그 승인 결과를 반영합니다.

게임 이벤트는 WebRTC DataChannel로 교환합니다. 이 구조는 대전 상태를 맞추기 위한 것으로, 호스트 조작까지 막는 서버 검증 구조는 아닙니다.

## 6. 재접속한 사람뿐 아니라 상대 보드도 초기화됐습니다

영상 연결 상태가 바뀔 때 게임 런타임이 함께 정리됐고, 복구 과정에서 상대방 보드까지 덮어쓰는 문제가 있었습니다.

게임 상태의 수명을 영상 연결과 분리하고, 재접속 복구는 대상 플레이어에게만 적용했습니다. 두 클라이언트로 접속해 한쪽을 새로고침하고, 남아 있는 보드와 복구 대상이 각각 유지되는 흐름을 확인했습니다.
