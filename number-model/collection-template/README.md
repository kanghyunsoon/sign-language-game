# 지숫자 촬영 템플릿

`participant_template`을 참가자마다 복사해 `p01`, `p02`, … 로 이름을 바꾸고 그 안 폴더에 사진을 넣는다. 폴더 이름이 곧 라벨이다.

```
<촬영 루트>/
  p01/  1/ 2/ … 10/ none/
  p02/  1/ 2/ … 10/ none/
```

이 구조여야 `extract_number_frames.py --layout participant` 가 참가자를 인식하고, `train_number_model.py` 가 **참가자 단위로 train/valid/test를 분리**한다. 같은 사람이 학습과 시험에 동시에 들어가면 성능 수치가 낙관적으로 나오고 목표 판정을 할 수 없다.

원본 사진은 저장소에 넣지 않는다. 저장소 밖(예: `C:\AITraining\number-model\captured\`)에 두고, 추출한 npz만 공유한다. 파이프라인 문서의 개인정보 원칙과 같다 — 사진은 로컬에 남기고 랜드마크와 익명 메타데이터만 옮긴다.

## 참가자 ID 규칙

- `p01` ~ `pNN` 만 사용한다. 실명·학번·이메일을 폴더명에 쓰지 않는다.
- 누가 `p03`인지는 저장소 밖 별도 메모로 관리한다.

## 왜 촬영이 필요한가

숫자 `9`가 어떤 분류기·특징 조합에서도 recall 0.833을 넘지 못한다. 랜드마크 경로와 이미지 CNN 경로가 **서로 독립인데 똑같이 0.833에서 멈췄다**(T-145, T-150, T-151, T-153). 표본 수 문제가 아니라 촬영 조건 다양성의 천장이다.

기존 KSL `9` 90장의 파일명이 `IMG_4562`~`IMG_4566` 처럼 연속이고 `KakaoTalk_…` 배치가 51장이다. 즉 촬영 세션 3~4개, signer 극소수다.

## 무엇을 얼마나

| 우선순위 | 라벨 | 이유 |
| --- | --- | --- |
| 1 | **`9`** | 유일한 미해결 class |
| 2 | **`8`** | 오류가 `9`→`8` 로 몰린다. 경계를 함께 학습해야 한다 |
| 3 | `1`, `4`, `10` | 그다음 취약군 |
| 4 | 나머지 + `none` | 여유가 되면 |

목표: **signer 5~8명 × 1인당 20~25장**. 합계 120~200장.

숫자를 늘리는 것보다 **`signer × 조건` 조합 수**가 중요하다. 같은 사람이 같은 자세로 100장을 더 찍으면 0.833에서 움직이지 않는다.

## 조건 분배

조건을 전부 통제할 필요는 없다. `feature_v3`가 손목 기준 이동과 손 크기를 정규화해 없애기 때문에 **거리는 대부분 사라지고, 조명은 좌표에 영향이 없다**(검출 성공률만 떨어뜨린다).

**카메라 각도도 일부러 바꾸지 않는다.** 서비스 인식이 정면에서만 일어나므로, 정면 외 각도는 모델이 볼 일이 없는 조건이다. 그런 조건에 학습 용량을 쓰면 낭비이고, `8`↔`9`처럼 미세한 차이로 갈리는 쌍에서는 회전 변화가 경계를 흐려 오히려 해롭다. T-144에서 기하 증강을 줄였을 때 가장 취약했던 모음들이 크게 오른 것도 같은 방향이다(`ㅜ` 0.750→0.929, `ㅣ` 0.778→0.963).

다만 `feature_v3`는 **회전 정규화를 하지 않으므로**(파이프라인 문서: *"손바닥 방향을 없애는 회전 정규화는 적용하지 않는다"* — 방향이 판별 신호다) 방향 변화가 완전히 0이어도 안 된다. 정면이라도 사람마다 손목 각도가 다르기 때문이다. 그 변화는 아래의 "손 내렸다 다시 올리기"가 공짜로 만들어 주며, 억지로 몸을 트는 것보다 **실제 사용 분포에 가깝다**.

라벨 하나당 12장(`8`·`9`는 24장):

| | 오른손 | 왼손 |
| --- | ---: | ---: |
| 카메라 정면 | 6장 | 6장 |

`8`·`9`는 각 12장. 좌/우손은 유지한다 — 게임에서 둘 다 나오고, MediaPipe가 handedness를 틀리면 미러링이 잘못 적용되는 실제 위험이 있다.

이 선택으로 **각도 강건성은 측정할 수 없게 된다.** 문서가 T-06부터 기록해온 "조건별 정확도 측정 불가"가 그대로 남는다는 뜻이며, 각도가 어긋난 프레임은 오확정이 아니라 미확정으로 이어진다(게임에서 더 안전한 실패 방향이고, 프론트가 1,200ms 창에서 유효 프레임 80%만 요구하므로 몇 프레임은 흡수된다).

## 촬영 시 지킬 것

- ⭐ **한 장 찍고 손을 완전히 내렸다가 다시 만들어서 다음 장.** 이것이 가장 중요하고 가장 값싼 다양성 확보 수단이다. 기존 KSL `9`가 `IMG_4562`~`IMG_4566`처럼 연속 버스트라 사실상 같은 사진이고, 그래서 90장인데도 recall 0.833에서 막혔다.
- **한 프레임에 손 하나만.** 추출기가 `num_hands=1`로 동작한다.
- 손이 프레임 밖으로 잘리지 않게 한다. 잘린 사진은 검출 실패로 버려진다(현재 실패율 약 4%).
- `10`이 두 형태가 있으면 한 형태로 통일하고 어느 쪽인지 기록한다. 라벨은 `10` 하나로 유지한다.
- jpg / jpeg / png / heic 모두 된다. EXIF 회전은 자동 보정된다.
- 해상도는 신경 쓰지 않아도 된다. 추출기가 긴 변 1024로 줄인다.

1인당 약 150장, 20분.

## 촬영 후

```bash
python number-model/scripts/extract_number_frames.py \
  --dataset C:\AITraining\number-model\captured \
  --output  C:\AITraining\number-model\features\number_captured_v3.npz \
  --layout participant \
  --source-name captured-2026 --license internal \
  --landmarker C:\AITraining\number-model\assets\hand_landmarker.task
```

그 뒤 학습에 공개 데이터와 함께 넘긴다. 참가자 ID가 없는 공개 데이터는 자동으로 train 전용이 되고, valid/test는 촬영 인원에서만 만들어진다.

```bash
python number-model/scripts/train_number_model.py \
  --features <공개 npz> <촬영 npz> \
  --output-dir number-model/models/number-10-v1 \
  --attempt-id T-1xx
```

`audit.json`의 `perLabel`과 `failed`를 먼저 확인한다. 특정 참가자에서 실패가 몰리면 촬영 조건을 고쳐 다시 찍는 편이 낫다.
