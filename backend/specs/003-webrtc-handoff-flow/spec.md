# Feature Specification: 방 실시간 연결 자동화 및 영상 통화 전환 시 안전한 정리

**Feature Branch**: `003-webrtc-handoff-flow`

**Created**: 2026-07-23

**Status**: Draft

**Input**: User description: "방 생성하고, 사용자가 들어오면 프론트에서 API호출과 웹 소켓 연결을 백엔드에 보내고 ... 영상 통화 연결이 성립되면 방 WebSocket 연결을 끊고, 클라이언트에서 게임이 끝나면 그때 API를 통해 백엔드에 게임 결과를 전달한다." 이후 논의를 통해 범위를 재조정: 영상 통화가 실제로 맺어지는지는 프론트엔드/네트워크 영역이며 필요한 백엔드 API(ICE 서버 조회, 시그널링 중계)는 이미 구현되어 있음(spec 002 US14). 이 스펙은 **(a) 아직 없는 백엔드 기능(방 입장 시 티켓 자동 동봉, 영상 통화 전환에 따른 의도된 WebSocket 종료 처리, 게임 타입/모드 구분, 모드별 결과 보고, 타입별 랭킹 분리)을 새로 만들고, (b) 이미 구현된 기존 기능(게임 시작 통보, ICE 서버 조회, 시그널링 중계)이 전체 흐름 안에서 계속 정상 동작하는지 회귀 검증**하는 것을 목적으로 한다.

**용어**: 게임 종류는 세 가지다 — **지문자 1:1 대전**(기존), **테트리스 대전**(2인), **테트리스 솔로**(1인). 앞의 둘을 묶어 **"대전 모드"**(방·실시간 연결·영상 통화가 필요), 마지막을 **"솔로 모드"**(상대가 없으므로 방/실시간 연결 자체가 필요 없고 결과 제출만 존재)라 부른다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 방에 입장하면 실시간 연결이 자동으로 맺어진다 (Priority: P1) — 신규

**대전 모드**(지문자 1:1 대전, 테트리스 대전) 방에 한해, 사용자가 게임방을 생성하거나 코드로 입장하면 별도의 추가 API 호출 없이 실시간 연결(방 안 상대방의 연결/이탈 상태를 실시간으로 알려주는 채널)이 즉시 수립된다. 지금은 방 입장에 성공한 뒤 실시간 연결용 인증 정보를 얻으려면 별도 API를 한 번 더 호출해야 한다. (솔로 모드는 애초에 "방"이라는 개념 자체가 없다 — User Story 8 참고)

**Why this priority**: 이후 모든 실시간 기능(게임 시작 통보, 영상 통화 시그널링)이 이 연결 위에서 동작하므로, 이게 자동으로 맺어지지 않으면 나머지 전부가 성립하지 않는다.

**Independent Test**: 방 생성 또는 입장 API를 한 번 호출한 뒤, 별도의 추가 API 호출 없이 그 응답 정보만으로 실시간 연결이 수립되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 로그인된 상태, **When** 대전 모드 게임방을 생성하면, **Then** 응답에 실시간 연결에 필요한 인증 정보가 함께 포함된다.
2. **Given** 유효한 방 코드가 있는 상태, **When** 그 방에 입장하면, **Then** 입장 응답에도 동일하게 실시간 연결용 인증 정보가 포함된다.
3. **Given** 응답으로 받은 인증 정보, **When** 그 정보만으로 실시간 연결을 시도하면, **Then** 별도의 추가 API 호출 없이 연결이 성립한다.

---

### User Story 2 - 영상 통화 연결로 전환하면 방 실시간 연결이 오작동 없이 정리된다 (Priority: P1) — 신규

두 참가자 사이의 영상 통화(WebRTC) 연결이 실제로 맺어지면, 더 이상 필요 없어진 방의 실시간 연결(WebSocket)을 클라이언트가 의도적으로 종료할 수 있다. 이때 시스템은 이 종료를 "참가자가 방을 나간 것"으로 착각해서는 안 된다. **지금은 이 구분이 없어서, 영상 통화 연결 후 방 실시간 연결을 끊으면 몇 초 뒤 시스템이 이를 예기치 않은 연결 끊김으로 판단해 그 참가자를 방에서 자동으로 내보내 버린다(결함).**

**Why this priority**: 이 결함을 그대로 두면, 정상적으로 영상 통화까지 성공한 사용자가 게임 도중 갑자기 방에서 제외되는 심각한 오류로 이어진다. 이번 스펙에서 반드시 고쳐야 할 핵심 대상이다.

**Independent Test**: 실시간 연결이 맺어진 상태에서 "영상 통화 연결됨, 의도적으로 종료함"을 알리고 연결을 끊으면, 참가자가 방에서 제외되지 않고 계속 참가 상태로 남는지 확인. 반대로 이 신호 없이 연결이 끊기면(네트워크 단절 등) 기존과 동일하게 유예 시간 후 이탈 처리되는지 확인(회귀 확인).

**Acceptance Scenarios**:

1. **Given** 실시간 연결이 아직 열려 있는 상태, **When** 클라이언트가 그 연결을 통해 "영상 통화로 전환했다"는 신호를 보낸 직후 같은 연결을 종료하면, **Then** 시스템은 이를 의도된 정리로 인식하고 참가자를 방에서 내보내지 않는다.
2. **Given** 위와 같이 정리가 완료된 상태, **When** 게임이 계속 진행되면, **Then** 해당 참가자는 계속 방의 정상 참가자로 남아 있다(재입장 불필요).
3. **Given** 실시간 연결이 맺어진 상태, **When** 위 신호 없이 연결이 예기치 않게 끊기면(네트워크 단절 등), **Then** 시스템은 기존과 동일하게 유예 시간을 두고 이탈을 처리한다(회귀 없음).
4. **Given** 게임 시작 후 일정 시간이 지나도 영상 통화 전환 신호가 오지 않은 상태, **When** 그 시간이 지나면, **Then** 방의 실시간 연결은 계속 유지되어 최소한의 연결 상태 감지 수단으로 남는다.

### User Story 3 - 게임 시작부터 영상 통화 연결까지, 기존 기능이 이어서 정상 동작한다 (Priority: P2) — 기존 기능 회귀 검증

양쪽 참가자가 준비를 마치고 방장이 시작을 요청하면 게임 시작이 통보되고, 클라이언트는 이미 구현되어 있는 API로 영상 통화 연결에 필요한 서버 정보를 받고, 신호를 중계받아 영상 통화 연결을 시도한다. 이 스토리는 새 기능이 아니라 **User Story 1·2로 흐름이 바뀐 뒤에도 기존 기능들이 이어서 문제없이 동작하는지 확인**하는 것이 목적이다. (대전 모드에만 해당 — 솔로 모드는 이 흐름 자체가 없다)

**Why this priority**: 새 기능(US1, US2) 자체는 이 연결 고리 없이도 독립적으로 검증 가능하지만, 실제 배포 전에는 전체 흐름이 끊기지 않고 이어지는지 확인이 필요하다.

**Independent Test**: 두 참가자가 모두 준비 완료 후 시작 요청이 성공하면, 두 참가자 모두 게임 시작을 통보받고, 이어서 ICE 서버 정보 조회와 시그널링 중계가 이전과 동일하게 동작하는지 확인.

**Acceptance Scenarios**:

1. **Given** 두 참가자가 모두 준비를 완료한 상태, **When** 방장이 시작을 요청하면, **Then** 두 참가자 모두 실시간 연결을 통해 즉시 게임 시작을 통보받는다. (기존 기능)
2. **Given** 게임 시작이 통보된 상태, **When** 클라이언트가 영상 통화 연결에 필요한 서버 정보를 조회하면, **Then** 정상적으로 응답을 받는다. (기존 기능)
3. **Given** 한쪽이 영상 통화 연결 신호(제안/응답/후보 경로)를 보내면, **Then** 같은 방의 상대방에게만 그 신호가 가공 없이 전달되고 다른 방 참가자에게는 전달되지 않는다. (기존 기능)

### User Story 4 - 대전 모드 게임이 끝나면 결과가 승패 정보만으로 안전하게 기록된다 (Priority: P1) — 일부 신규

대전 모드(지문자 1:1 대전, 테트리스 대전) 게임이 끝나면 클라이언트는 점수 없이 승패 정보만 API로 보고하고, 백엔드는 이를 안전하게(중복 없이) 기록한다. 결과 보고 자체(엔드포인트, 중복 방지)는 기존 기능이지만, "점수를 필수로 받아 비교해서 승자를 계산하는" 지금 방식은 바뀐다 — 점수 없이 승자 정보만 받는 것으로.

**Why this priority**: 지금 방식(점수 비교로 승자 결정)은 대전 모드에 불필요한 값을 강제한다. 결과 기록은 랭킹·전적의 근거 데이터라 정확성이 중요하다.

**Independent Test**: 대전 모드 방에서 점수 없이 승자 정보만으로 결과를 보고해도 정상 기록되는지, 같은 방에 대해 중복 보고를 시도하면 거부되는지 확인.

**Acceptance Scenarios**:

1. **Given** 대전 모드 게임이 진행 중인 방, **When** 클라이언트가 게임 종료 후 승자 정보만 보고하면(점수 없이), **Then** 결과가 기록되고 참가자들의 전적(승수)에 반영된다.
2. **Given** 이미 결과가 보고되어 종료된 방, **When** 같은 방에 대해 결과 보고를 다시 시도하면, **Then** 거부되고 중복 기록되지 않는다.
3. **Given** 방 참가자가 아닌 사용자, **When** 그 방의 결과 보고를 시도하면, **Then** 거부된다.

---

### User Story 5 - 게임이 끝나면 방은 다시 대기 상태로 돌아가 재대결할 수 있다 (Priority: P2) — 신규

대전 모드에서 결과가 보고되면 방은 곧바로 종료(CLOSED)되지 않고 대기(WAITING) 상태로 돌아간다. 두 참가자가 모두 남아있다면 준비 상태가 초기화되어, 같은 방에서 다시 준비를 마치고 재대결을 시작할 수 있다. (솔로 모드는 애초에 방이 없으므로 해당 없음)

**Why this priority**: 매번 새 방을 만들지 않고도 같은 상대와 반복 대결할 수 있게 해 재사용성을 높인다.

**Independent Test**: 결과 보고가 완료된 직후 방 상태가 WAITING인지, 두 참가자의 준비 상태가 초기화됐는지, 참가자 구성(인원)은 그대로 유지되는지 확인. 이어서 참가자가 그 방에 재입장을 시도하면 새 실시간 연결 정보를 받아 다시 연결할 수 있는지 확인.

**Acceptance Scenarios**:

1. **Given** 게임이 진행 중이고 두 참가자 모두 아직 방에 남아있는 상태, **When** 결과가 보고되면, **Then** 방은 WAITING 상태로 돌아가고 양쪽의 준비 상태는 초기화되며 인원 구성은 그대로 유지된다.
2. **Given** 방이 WAITING으로 복귀한 상태, **When** 참가자가 다시 그 방에 입장을 시도하면(기존 재입장 인식 로직 재사용), **Then** 새로운 실시간 연결 인증 정보를 받아 다시 연결할 수 있다.
3. **Given** 상대방이 결과 보고 이전에 명시적으로 방을 나가(`POST /leave`) 방이 이미 CLOSED로 전환된 상태(서버는 게임 진행 중 실시간 이탈을 감지하지 못하므로, 이 경우만 서버가 알 수 있는 유일한 "이미 나감" 경로다 — FR-007), **When** 그 방에 결과를 보고하려 하면, **Then** 기존 규칙(IN_PROGRESS가 아닌 방은 결과 보고 거부)에 따라 그대로 거부되며, 별도의 새 로직이 필요하지 않다.
4. **Given** 방이 WAITING으로 복귀한 상태, **When** 로비에서 실시간 목록을 구독 중인 사용자가 있다면, **Then** 그 방이 다시 대기 중인 방 목록에 나타난다.

### User Story 6 - 대전 모드 게임방은 게임 종류를 구분해서 생성된다 (Priority: P1) — 신규

사용자가 대전 모드 게임방을 생성할 때 게임 종류(지문자 1:1 대전 또는 테트리스 대전)를 지정한다. 지금은 게임방이 지문자 1:1 대전 하나만 존재한다는 전제로 되어 있다. (솔로 모드는 이 "게임방" 개념 자체를 쓰지 않는다 — User Story 8 참고)

**Why this priority**: 게임 종류 구분이 없으면 테트리스 대전을 지원할 방법이 없다. MVP 완성에 필수적인 기반 요구사항이다.

**Independent Test**: 방 생성 시 게임 종류를 지정하고, 응답과 로비 실시간 목록에 그 종류가 정확히 노출되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 로그인된 상태, **When** 게임 종류를 지정해 대전 모드 방을 생성하면, **Then** 그 종류로 방이 만들어지고 응답에 포함되며 정원은 2명이다.
2. **Given** 게임 종류를 지정하지 않은 상태, **When** 방 생성을 시도하면, **Then** 거부된다.
3. **Given** 서로 다른 종류의 방이 섞여 있는 상태, **When** 로비 실시간 목록을 조회하면, **Then** 각 방의 게임 종류가 함께 노출된다.

### User Story 8 - 테트리스 솔로는 방/실시간 연결 없이 결과만 보고하면 끝난다 (Priority: P1) — 신규

테트리스 솔로는 상대가 없다. **게임방을 만들지 않고, 실시간 연결도 없고, 심지어 "시작"을 알리는 API조차 없다.** 사용자는 클라이언트에서 자유롭게 플레이한 뒤, 게임이 끝나면 **점수를 보고하는 API 하나만** 호출하면 끝이다.

**Why this priority**: 솔로 모드에 대전 모드와 같은 방/실시간 연결/준비-시작 개념을 적용하면 상대가 없는데도 불필요한 절차가 강제된다. 가장 단순한 형태로 유지하는 것 자체가 핵심 요구사항이다.

**Independent Test**: 방 생성이나 실시간 연결, 시작 API 호출 없이 곧바로 점수 보고 API만 호출해도 결과가 정상 기록되는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자, **When** 테트리스 솔로를 플레이한 뒤 점수를 보고하면, **Then** 그 즉시 결과가 기록된다 — 그 전에 방 생성이나 실시간 연결, 별도의 "시작" API 호출이 없어도 된다.
2. **Given** 솔로 결과 보고, **When** 요청에 승자/상대방 정보가 포함되면, **Then** 그런 정보는 애초에 필요하지 않다(점수만 있으면 된다).
3. **Given** 솔로 모드, **When** 어떤 클라이언트가 방 생성이나 실시간 연결(WebSocket) 수립을 시도하면, **Then** 그럴 이유도 방법도 없다(대전 모드 전용 API이므로 애초에 대상이 아님).

---

### User Story 9 - 랭킹은 게임 종류별로 완전히 분리되어 보여진다 (Priority: P2) — 신규

세 게임 종류(지문자 1:1 대전, 테트리스 대전, 테트리스 솔로)는 각각 완전히 독립된 랭킹을 갖는다. 하나로 합쳐진 통합 랭킹은 없다. 대전에 속하는 두 종류(지문자 1:1 대전, 테트리스 대전)는 각각 승수 기준으로, 솔로(테트리스 솔로)는 최고 점수 기준으로 순위를 매긴다.

**Why this priority**: 서로 다른 게임의 승패 기록과 점수 기록은 성격이 달라 하나의 랭킹으로 합칠 수 없다.

**Independent Test**: 서로 다른 종류로 플레이한 기록이 섞여 있는 상태에서 특정 종류의 랭킹을 조회했을 때, 그 종류의 기록만 반영되고 다른 종류의 결과가 섞이지 않는지 확인.

**Acceptance Scenarios**:

1. **Given** 여러 사용자가 서로 다른 게임 종류로 플레이한 기록이 있는 상태, **When** 특정 게임 종류의 랭킹을 조회하면, **Then** 그 종류의 결과만 반영된 순위가 반환된다.
2. **Given** 지문자 1:1 대전 또는 테트리스 대전, **When** 그 종류의 랭킹을 조회하면, **Then** 승수 기준으로 정렬된 순위가 반환된다.
3. **Given** 테트리스 솔로, **When** 랭킹을 조회하면, **Then** 최고 점수 기준으로 정렬된 순위가 반환된다.
4. **Given** 사용자가 특정 종류에서 한 번도 플레이하지 않은 상태, **When** 그 종류의 랭킹을 조회하면, **Then** 해당 사용자는 그 랭킹에 나타나지 않는다.

---

### User Story 10 - 준비 상태 변경이 상대방에게 실시간으로 전달된다 (Priority: P1) — 신규

대전 모드에서 참가자가 준비 상태를 바꾸면(API로 요청), 그 변경이 같은 방의 상대방에게 실시간 연결(WebSocket)을 통해 즉시 전달된다. **지금은 이 전달이 없다** — 준비 상태 변경은 REST 응답으로 요청자 본인에게만 알려지고, 상대방은 그 사실을 알 방법이 없어 직접 다시 조회(폴링)해야 한다.

**Why this priority**: 상대방의 준비 여부를 실시간으로 알 수 없으면 "언제 시작 버튼을 누를 수 있는지" 프론트가 폴링에 의존하게 되어 반응이 느려지고 불필요한 요청이 늘어난다. 게임 시작 전 핵심 상호작용이므로 우선순위를 높게 둔다.

**Independent Test**: 한쪽이 준비 상태를 변경하면, 별도 조회 없이 상대방의 실시간 연결로 그 변경이 도착하는지 확인.

**Acceptance Scenarios**:

1. **Given** 두 참가자 모두 실시간 연결이 맺어진 상태, **When** 한쪽이 준비 완료로 상태를 바꾸면, **Then** 상대방은 별도 조회 없이 실시간 연결을 통해 그 변경을 즉시 통보받는다.
2. **Given** 준비 완료 상태였던 참가자, **When** 준비를 취소하면, **Then** 그 변경도 동일하게 상대방에게 즉시 통보된다.
3. **Given** 실시간 연결이 아직 없는(또는 끊긴) 상대방, **When** 참가자가 준비 상태를 바꾸면, **Then** 시스템은 이를 안전하게 처리한다(전달 실패가 API 자체를 실패시키지 않음).

---

### Edge Cases

- 클라이언트가 "영상 통화로 전환했다"는 신호를 보냈지만 실제로는 영상 통화 연결에 실패한 상태라면 어떻게 되는가? (신호는 클라이언트의 자체 판단을 그대로 신뢰하며, 시스템이 실제 영상 통화 성립 여부를 검증하지는 않는다)
- 신호를 보낸 직후, 실시간 연결이 종료되기 전에 상대방이 실제로 이탈하면 어떻게 되는가?
- 같은 참가자가 신호를 중복으로 여러 번 보내면 어떻게 되는가?
- 두 참가자 모두 영상 통화 연결에 실패하는 네트워크 환경이면 어떻게 되는가? (신호가 오지 않으므로 방 실시간 연결이 계속 유지됨 — User Story 2 시나리오 4)
- 게임이 시작되기 전(영상 통화 전환 전)에 한쪽이 이탈하면 어떻게 되는가? (기존 이탈 처리 범위 — 이 스펙에서 새로 정의하지 않음)
- 클라이언트가 결과를 보고하기 전에 브라우저를 닫아버리면 어떻게 되는가? (User Story 2에 따라 실시간 이탈 감지는 하지 않으므로, 결과가 영구히 보고되지 않을 수 있음 — Assumptions 참고)
- 결과를 보고한 클라이언트는 방이 WAITING으로 복귀했음을 알지만, 보고하지 않은 다른 클라이언트는 그 사실을 어떻게 아는가? (Assumptions 참고 — 별도 실시간 통보 없이, 게임 종료를 각자 인지한 뒤 독립적으로 방에 재입장을 시도하는 것으로 처리한다)
- 재대결 준비 중(WAITING 복귀 후) 한쪽이 다시 나가면 어떻게 되는가? (기존 이탈 처리 범위 재사용 — 새로 정의하지 않음)
- 대전 모드 결과가 무승부면 어떻게 보고하는가? (승자 정보를 비워서 보내면 무승부로 처리되고 승패 어느 쪽에도 반영되지 않음 — 기존 동작과 동일, FR-033)
- 대전 모드 방 생성 후 게임 종류를 나중에 바꿀 수 있는가? (변경 불가 — Assumptions 참고)
- 솔로 결과를 같은 사용자가 짧은 시간에 여러 번 보고하면 어떻게 되는가? (모두 개별 기록으로 남고 각각 랭킹에 반영될 수 있음 — 중복 방지 개념 자체가 없음, Assumptions 참고)
- 탈퇴한 사용자의 기록은 어느 랭킹에서도 제외되는가? (기존 스펙의 탈퇴 사용자 제외 규칙이 세 랭킹 모두에 동일하게 적용된다고 가정)
- 상대방이 아직 실시간 연결을 맺기 전(입장 확인 대기 중)에 준비 상태를 바꾸면 통보는 어떻게 되는가? (상대방 연결이 없으므로 통보 자체가 실패하지만 API 요청은 정상 처리됨 — User Story 10 시나리오 3)

## Requirements *(mandatory)*

### Functional Requirements — 신규 (대전 모드: 실시간 연결/전환)

- **FR-001**: 시스템은 대전 모드 방의 생성 및 입장 API 응답에 실시간 연결 수립에 필요한 인증 정보를 포함해야 한다.
- **FR-002**: 사용자가 대전 모드 방 생성 또는 입장에 성공하면, 그 응답만으로(추가 API 호출 없이) 실시간 연결이 즉시 수립될 수 있어야 한다.
- **FR-003**: 시스템은 클라이언트가 "영상 통화 연결로 전환했으므로 방의 실시간 연결을 의도적으로 종료한다"는 신호를, **그 실시간 연결이 아직 열려 있는 동안** 같은 연결을 통해 보낼 수 있게 해야 한다(연결을 끊은 뒤에는 이 신호를 보낼 수 없다).
- **FR-004**: 시스템은 이 신호를 받은 연결이 그 직후 종료되면, 이를 참가자의 방 이탈로 처리하지 않고 해당 참가자를 계속 정상 참가자로 유지해야 한다.
- **FR-005**: 시스템은 이 신호 없이 방의 실시간 연결이 종료되는 경우, 기존과 동일하게 예기치 않은 연결 끊김으로 간주해 유예 시간을 두고 이탈을 처리해야 한다(회귀 없음).
- **FR-006**: 게임 시작 후 일정 시간 안에 이 신호가 오지 않으면, 시스템은 방의 실시간 연결(WebSocket)을 종료하지 않고 유지해 최소한의 연결 상태 감지 수단으로 사용해야 한다.
- **FR-007**: 방의 실시간 연결이 (신호에 따라) 정리된 이후에는, 시스템은 게임 진행 중 참가자 이탈을 실시간으로 감지하지 않으며, 결과 보고 시점(FR-011)에 요청자가 유효한 방 참가자인지를 검증하는 것으로 이탈 여부를 사후적으로 다룬다.

### Functional Requirements — 신규 (대전 모드: 방/결과/랭킹)

- **FR-013**: 시스템은 대전 모드에서 게임 결과가 보고되면 방을 즉시 종료(CLOSED)하지 않고, 두 참가자가 모두 남아있다면 대기(WAITING) 상태로 되돌리고 양쪽의 준비 상태를 초기화해야 한다.
- **FR-014**: 시스템은 결과 보고 시점에 참가자가 한 명만 남아있다면, 기존 방 나가기 처리 규칙(방장 위임 또는 인원 0명 시 종료)을 그대로 적용해야 하며 별도 규칙을 두지 않는다.
- **FR-015**: 시스템은 방이 대기(WAITING) 상태로 복귀하면, 로비 실시간 목록에도 다시 노출해야 한다.
- **FR-016**: 시스템은 이미 등록된 참가자가 대기 상태로 복귀한 방에 다시 입장을 시도하면, 새로운 실시간 연결 인증 정보를 발급해야 한다(FR-001/002와 동일한 방식 재사용).
- **FR-017**: 시스템은 대전 모드 방 생성 시 게임 종류(지문자 1:1 대전 / 테트리스 대전)를 필수로 받아야 하며, 지정되지 않으면 생성을 거부해야 한다.
- **FR-018**: 시스템은 방 정보(생성/입장 응답, 로비 실시간 목록)에 게임 종류를 포함해야 한다.
- **FR-020**: 시스템은 대전 모드 방의 정원을 2명으로 적용해야 한다.
- **FR-021**: 시스템은 대전 모드 방의 결과 보고 시 점수 없이 승자 정보만 받아 기록해야 한다(점수 비교 방식은 폐기).
- **FR-033**: 시스템은 승자 정보가 비어있는(무승부) 결과 보고를 허용해야 하며, 이 경우 어느 쪽의 승패에도 반영하지 않아야 한다(기존 무승부 처리 방식과 동일, 회귀 없음).
- **FR-030**: 시스템은 대전 모드에서 참가자의 준비 상태가 변경되면, 이미 수립된 실시간 연결을 통해 같은 방의 상대방에게 즉시 그 변경을 통보해야 한다.
- **FR-031**: 시스템은 상대방의 실시간 연결이 없거나 끊긴 상태에서 준비 상태 변경이 발생해도, 그 통보 실패가 준비 상태 변경 API 자체의 실패로 이어지지 않아야 한다.
- **FR-025**: 시스템은 게임 종류 3종(지문자 1:1 대전 / 테트리스 대전 / 테트리스 솔로) 각각에 대해 완전히 독립된 랭킹을 제공해야 하며, 서로 다른 종류의 결과가 하나의 랭킹에 합쳐지지 않아야 한다.
- **FR-026**: 시스템은 지문자 1:1 대전과 테트리스 대전 각각의 랭킹을 승수 기준으로 산정해야 하며, 승수가 같으면 패수가 더 적은 쪽을 상위로 산정해야 한다(기존 랭킹의 동률 처리 규칙과 동일, 회귀 없음).
- **FR-032**: 시스템은 기존 `users.win_count`/`loss_count`에 저장되어 있던 지문자 1:1 대전 전적을, 새로운 공통 저장 구조(게임 종류별 개별 기록)로 마이그레이션해야 하며, 이후 두 컬럼에 더 이상 의존하지 않아야 한다.

### Functional Requirements — 신규 (솔로 모드: 완전히 별도)

- **FR-027**: 시스템은 테트리스 솔로 결과를 보고하는 API를 대전 모드의 게임방 개념과 완전히 별도로 제공해야 한다 — 방 생성, 실시간 연결, 준비/시작 절차를 전혀 요구하지 않는다.
- **FR-028**: 시스템은 이 API로 점수만 받아 기록해야 하며, 승자·상대방 정보는 요구하지 않는다.
- **FR-029**: 시스템은 테트리스 솔로의 랭킹을 최고 점수 기준으로 산정해야 한다.

### Functional Requirements — 기존 기능 회귀 검증 대상 (이미 구현됨, 변경 없음)

- **FR-008**: 시스템은 양쪽 참가자가 모두 준비를 완료하고 시작 요청이 승인되면, 이미 수립되어 있는 실시간 연결을 통해 두 참가자 모두에게 즉시 게임 시작을 통보해야 한다.
- **FR-009**: 시스템은 클라이언트가 영상 통화 연결에 필요한 서버 정보를 조회할 수 있는 수단을 제공해야 한다.
- **FR-010**: 시스템은 같은 방의 두 참가자 사이에 오가는 영상 통화 연결 신호를 내용을 변경하지 않고 그대로 중계해야 하며, 다른 방의 참가자에게는 전달되지 않아야 한다.
- **FR-011**: 시스템은 대전 모드 게임 종료 후 클라이언트가 결과(승자 정보)를 API로 보고할 수 있게 해야 하며, 이미 결과가 보고된 게임에 대한 중복 보고는 거부해야 한다.
- **FR-012**: 시스템은 해당 방의 참가자가 아닌 사용자의 실시간 연결 수립 시도 및 결과 보고 시도를 거부해야 한다.

> 번호 참고: FR-019, FR-022~024는 이전 초안(게임 종류 3가지 모두를 "방" 개념으로 다루던 버전)에서 쓰였다가 이번 재구성으로 제거된 결번이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 대전 모드 방 생성/입장에 성공한 시점부터 3초 이내에 실시간 연결이 수립된다.
- **SC-002**: "영상 통화로 전환했다"는 신호를 보내고 실시간 연결을 종료해도, 정상적으로 게임 중인 참가자가 방에서 의도치 않게 제외되는 사례가 0건이다.
- **SC-003**: 이 신호 없이 연결이 예기치 않게 끊긴 경우, 100%의 사례에서 기존과 동일한 유예 시간·이탈 처리가 그대로 동작한다(회귀 없음).
- **SC-004**: 양쪽 참가자가 준비를 완료하고 시작을 요청한 시점부터 2초 이내에 두 참가자 모두 게임 시작을 통보받는다(기존 기능 검증).
- **SC-005**: 대전 모드 게임 결과는 100% 정확히 한 번만 기록되며, 중복 보고로 인한 데이터 오염이 발생하지 않는다.
- **SC-006**: 결과 보고가 완료된 시점부터 3초 이내에 방이 대기(WAITING) 상태로 로비 실시간 목록에 다시 나타난다.
- **SC-007**: 솔로 모드는 결과 보고 API 호출 하나만으로 100% 완결되며, 그 앞뒤로 방 생성이나 실시간 연결 시도가 0건이다.
- **SC-008**: 세 게임 종류의 랭킹이 서로 완전히 독립적으로 조회되며, 한 종류의 결과가 다른 종류 랭킹에 영향을 주는 사례가 0건이다.
- **SC-009**: 준비 상태 변경 API 호출 시점부터 1초 이내에 상대방이 실시간 연결로 그 변경을 통보받는다.

## Assumptions

- 방 생성/입장 API 응답에 실시간 연결용 단기 인증 정보(티켓)를 함께 내려주는 것으로 가정한다(FR-001/002) — 기존에는 별도 API로 발급받아야 했으나, 이번 스펙에서 응답에 동봉하는 것으로 범위를 정한다.
- "영상 통화로 전환했다"는 신호는 클라이언트의 자체 판단을 그대로 신뢰하며, 시스템이 실제로 영상 통화가 연결되었는지를 검증하지는 않는다(검증 수단이 없음 — 서버는 두 클라이언트 사이의 P2P 연결 상태를 알 수 없다).
- 이 신호는 **방의 실시간 연결(WebSocket)이 아직 열려 있는 동안 그 연결을 통해** 보낸다 — 별도의 REST API를 새로 호출하는 방식은 아니다. 정확한 메시지 형식(타입 이름 등)은 이 스펙에서 정하지 않으며 계획 단계에서 정한다.
- 영상 통화에 필요한 STUN/TURN 서버 정보는 연결을 시도하는 시점에 한 번에 모두 제공되며(이미 구현됨), "우선 시도 후 실패하면 재조회"하는 별도 절차는 두지 않는다.
- 실제 게임 진행 데이터(문제 배포, 정답 판정, 점수 계산 등)를 주고받는 방식은 이 스펙의 범위 밖이며, 별도 담당 영역에서 정의한다.
- 방 실시간 연결이 정리된 이후에는 게임 중 상대방 이탈을 실시간으로 알려주지 않는다(FR-007) — 한쪽이 게임 도중 나가거나 결과를 끝내 보고하지 않으면, 남은 참가자는 그 사실을 알 방법이 없고 방은 결과 보고 없이 방치될 수 있다. 방치된 방의 자동 정리는 기존 스펙(002, US4/US15)의 정리 스케줄러 범위에 맡긴다.
- 게임 종료 시점 자체(클라이언트가 매치가 끝났다고 판단하는 시점)는 이 스펙 범위 밖의 게임 진행 로직에서 결정된다. 결과를 보고하지 않은 나머지 참가자에게 "방이 재대결 가능 상태가 됐다"를 실시간으로 알려주는 별도 채널은 두지 않으며, 각자 독립적으로 방에 재입장을 시도해 새 연결 정보를 받는 흐름(FR-016)을 기본값으로 삼는다.
- 재대결 시작(다시 준비 완료 후 시작 요청)은 기존 준비/시작 API를 그대로 재사용하며 새로 정의하지 않는다.
- 대전 모드 방의 게임 종류는 생성 시 한 번 정해지며 이후 변경되지 않는다(FR-017).
- 기존에 이미 존재하는 지문자 1:1 대전 방 데이터는 마이그레이션 시 그대로 지문자 1:1 대전 종류로 취급된다.
- 영상 통화(시그널링) 관련 흐름(User Story 2~5, FR-003~010)은 대전 모드의 두 게임 종류(지문자 1:1 대전, 테트리스 대전) 모두에 동일하게 적용된다.
- 대전 모드 방의 실시간 연결이 게임 진행 중 정확히 어떻게 쓰이는지(시그널링 이후의 게임 데이터 교환)와, 솔로 모드의 실제 진행 방식(입력 처리 등)은 이 스펙의 범위 밖이며 게임 파트가 별도로 정의한다.
- **솔로 모드는 "게임방(GameRoom)" 개념을 전혀 쓰지 않는다.** room_code 발급, 생성/입장, 정원, 준비/시작 같은 개념이 전부 해당 없음 — 클라이언트가 알아서 플레이하고 끝나면 점수 보고 API 하나만 호출한다(FR-027/028). 데이터 저장은 `game_rooms`/`game_sessions`와는 무관하지만, **세 게임 종류가 공유하는 "게임 종류 + 점수" 공통 저장 구조(아래 항목 참고) 위에 함께 기록된다** — 솔로만의 별도 전용 테이블을 새로 만들지 않는다.
- **솔로 결과에는 위·변조 여부를 검증하는 절차가 없다(의도적 결정).** 세션 존재 여부·경과 시간·점수 상한 등의 최소 검증도, 동일 결과 중복 방지도 이 스펙에서는 넣지 않는다. 점수 조작·중복 제출 가능성을 의식적으로 감수하는 것이며, 랭킹 신뢰도가 문제가 되면 이후 별도 스펙에서 검증/중복 방지 로직을 추가하는 것으로 한다.
- 랭킹은 게임 종류별로 각각 별도의 조회 API/화면으로 제공되며, 세 종류를 합산한 통합 랭킹은 이 스펙 범위에서 제공하지 않는다(FR-025).
- 준비 상태 변경 통보(FR-030)는 기존 `PEER_DISCONNECTED`/`RECONNECTED`/`LEFT`/`GAME_STARTED`와 같은 방식으로 방 실시간 연결 위의 새 메시지 타입으로 추가된다. 정확한 메시지 이름·payload 형식은 이 스펙에서 정하지 않으며 계획 단계에서 정한다(`realtime-websocket-messages.md` 갱신 필요).
- **세 게임 종류 모두 "게임 종류 + 점수" 형태의 공통 저장 구조로 통일한다.** 기존 `users.win_count`/`loss_count`(001/002 스펙 기준)도 예외로 남기지 않고 이 구조로 옮긴다 — 기존 데이터를 안전하게 옮기는 마이그레이션 비용이 낮아 굳이 옛 방식을 병행 유지할 이유가 없다는 판단이다. 대전 모드(지문자 1:1 대전, 테트리스 대전)는 승리 시 점수 1, 패배 시 점수 0을 기록해(무승부는 기록 없음, FR-033) 랭킹 집계 시 합산(SUM)하면 승수가 되고 패수도 함께 계산할 수 있다(FR-026의 동률 처리에 필요 — 기존 `users.loss_count` 기반 동률 규칙을 그대로 재현하려면 패배 기록이 있어야 한다). 솔로 모드(테트리스 솔로)는 실제 점수를 그대로 기록해 랭킹 집계 시 최댓값(MAX)을 취하면 최고 점수가 된다 — 저장 구조는 동일하고 랭킹 조회 시 게임 종류별로 집계 함수만 다르게 적용한다.
  - **마이그레이션**: 기존 `users.win_count`/`loss_count` 값은 지문자 1:1 대전 종류의 개별 기록으로 백필한 뒤, 두 컬럼은 제거하거나 더 이상 갱신하지 않는 것으로 정리한다. `users.win_count`/`loss_count`를 직접 참조하는 기존 코드(예: 프로필 조회 응답 등)가 있다면 새 집계 조회로 대체해야 한다 — 정확한 영향 범위는 계획 단계에서 확인한다.
  - **참고**: 이건 정규화가 아니라 하나의 `score` 컬럼이 게임 종류에 따라 다른 의미(승패 표시 vs 실제 점수)를 갖는 다형적(polymorphic) 테이블 설계다. 컬럼 하나가 문맥에 따라 의미가 갈리므로 값의 일관성(예: 대전 결과에 1/0이 아닌 값이 들어가는 것)을 DB가 아니라 애플리케이션 레벨에서 검증해야 한다는 트레이드오프가 있다. 정확한 테이블/컬럼 설계는 계획 단계에서 정한다.
