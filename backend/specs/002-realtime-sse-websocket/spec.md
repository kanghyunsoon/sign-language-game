### User Story 1 - 인증/인가 실패 응답 형식 통일 (Priority: P1)

API를 호출하는 모든 클라이언트(프론트엔드, 향후 게임 파트 서버 등)는 인증(401)·인가(403) 실패 시에도 다른 모든 API 오류와 동일한 형식의 오류 응답을 받아, 오류 처리 로직을 오류 종류별로 분기하지 않고 하나의 공통 규칙으로 다룰 수 있어야 한다.

**Why this priority**: 이후 추가되는 모든 실시간 인증(단기 티켓, WebSocket 핸드셰이크)도 결국 401/403을 반환하게 되므로, 오류 응답 형식이 먼저 통일되어 있지 않으면 실시간 계층에서 오류 처리가 이중화된다. 가장 먼저 끝내야 하는 선행 작업이다.

**Independent Test**: 인증 토큰 없이 보호된 API를 호출했을 때와, 다른 사용자의 리소스에 접근을 시도했을 때 반환되는 오류 응답 바디의 필드 구성이, 존재하지 않는 리소스 조회 등 이미 존재하는 일반 오류 응답과 동일한 스키마인지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 인증 토큰 없이 요청, **When** 인증이 필요한 API를 호출하면, **Then** 401 상태 코드와 함께 다른 API 오류와 동일한 필드 구성의 오류 응답 바디를 받는다.
2. **Given** 유효하지만 권한이 없는 인증 토큰, **When** 접근이 허용되지 않는 리소스를 요청하면, **Then** 403 상태 코드와 함께 동일한 오류 응답 형식을 받는다.
3. **Given** 만료되었거나 위조된 토큰, **When** 보호된 API를 호출하면, **Then** 401 상태 코드와 함께 동일한 오류 응답 형식을 받는다.

### User Story 2 - 동시 요청에 따른 게임방 데이터 정합성 보장 (Priority: P2)

같은 게임방에 대해 여러 요청(입장, 준비 상태 변경, 시작 등)이 거의 동시에 들어와도, 시스템은 나중에 처리된 요청이 앞선 변경 사항을 조용히 덮어쓰지 않도록 보장해야 한다.

**Why this priority**: 실시간 계층이 도입되면 같은 방에 대한 동시 요청 빈도가 크게 늘어난다(입장 직후 준비, 재접속과 나가기가 겹치는 경우 등). 동시성 보호가 먼저 갖춰져야 그 위에 실시간 브로드캐스트를 안전하게 쌓을 수 있다.

**Independent Test**: 같은 게임방에 대해 두 개의 상태 변경 요청을 인위적으로 동시에 보냈을 때, 하나는 정상 처리되고 다른 하나는 최신 상태가 아니라는 사유로 명확히 거부되는지(둘 다 성공한 것처럼 응답하지 않는지) 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 동일한 게임방에 대한 두 개의 변경 요청이 서버에 거의 동시에 도달한 상황, **When** 두 요청이 같은 데이터를 기준으로 각자 처리를 시도하면, **Then** 하나만 반영되고 다른 하나는 이미 데이터가 변경되었다는 사유로 거부된다.
2. **Given** 충돌로 거부된 요청, **When** 그 오류 응답을 확인하면, **Then** 다른 API 오류와 동일한 형식으로 재시도가 필요함을 알 수 있는 사유가 포함되어 있다.

---

### User Story 3 - 준비 상태 변경은 대기 중인 방에서만 허용 (Priority: P3)

게임이 이미 시작되었거나 종료된 방에서는 참가자가 준비 상태를 변경할 수 없어야 한다.

**Why this priority**: 사소해 보이지만, 실시간 계층에서 준비 상태 변경이 곧바로 다른 참가자에게 브로드캐스트되는 구조로 확장되므로, 유효하지 않은 시점의 상태 변경을 먼저 막아두지 않으면 이미 끝난 게임에 대한 오해를 유발하는 알림이 나갈 수 있다.

**Independent Test**: 이미 시작되었거나 종료된 방에서 준비 상태 변경을 시도했을 때 요청이 거부되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 아직 시작되지 않은(대기 중) 방의 참가자, **When** 준비 상태를 변경하면, **Then** 정상적으로 반영된다.
2. **Given** 이미 진행 중이거나 종료된 방의 참가자, **When** 준비 상태 변경을 시도하면, **Then** 요청이 거부된다.

---

### User Story 4 - 방치된 대기방 자동 정리 (Priority: P4)

아무도 시작하지 않고 오랫동안 방치된 대기 중인 방은, 이미 종료된 방과 마찬가지로 시스템이 주기적으로 자동 정리해야 한다.

**Why this priority**: 실시간 로비 목록(Part B)이 항상 최신 대기 방만 노출하려면, 방치된 방이 무한정 쌓이지 않아야 한다. 목록 자체를 만들기 전에 방 누수부터 막아야 목록이 의미를 갖는다.

**Independent Test**: 일정 기간 이상 대기 상태로 방치된 방과, 그렇지 않은 대기 방을 함께 두고 정리 작업을 실행했을 때, 방치된 방만 삭제되고 나머지(정상 대기 중, 진행 중, 이미 종료된 지 얼마 안 된 방)는 그대로인지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 설정된 보관 기간을 초과해 대기 상태로 방치된 방, **When** 정리 작업이 실행되면, **Then** 해당 방은 삭제된다.
2. **Given** 보관 기간 이내의 대기 중인 방 또는 진행 중인 방, **When** 정리 작업이 실행되면, **Then** 삭제되지 않고 그대로 유지된다.
3. **Given** 이미 종료(CLOSED)된 지 오래된 방, **When** 정리 작업이 실행되면, **Then** 기존과 동일하게 삭제된다(기존 동작 유지).

---

### User Story 5 - 백그라운드 정리 작업과 향후 실시간 신호 발송이 서로를 지연시키지 않음 (Priority: P5)

시스템 운영자 입장에서, 주기적으로 실행되는 여러 백그라운드 작업(방 정리, 향후 추가될 연결 유지 신호 발송 등)이 하나의 처리 지연으로 인해 서로를 밀리게 만들지 않아야 한다.

**Why this priority**: 실시간 계층이 도입되면 짧은 주기로 반복 실행되는 백그라운드 작업(연결 유지 신호 등)이 새로 추가된다. 기존 방 정리 작업과 자원을 다투면 실시간성이 저하되므로, 실시간 계층을 얹기 전에 백그라운드 작업 간 독립성을 먼저 보장해야 한다.

**Independent Test**: 여러 개의 주기적 백그라운드 작업을 동시에 등록해 두었을 때, 하나의 작업이 오래 걸리는 상황을 흉내내도 다른 작업의 실행 주기가 그로 인해 밀리지 않는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 여러 개의 주기적 백그라운드 작업이 등록되어 있는 상태, **When** 그 중 하나의 실행이 지연되면, **Then** 다른 작업들은 각자의 예정된 주기대로 계속 실행된다.

---

### User Story 6 - 게임방 API 응답이 내부 구현에 종속되지 않음 (Priority: P6)

게임방 관련 API를 호출하는 클라이언트는, 서버 내부의 데이터 표현 방식이 바뀌더라도 영향받지 않는 안정적인 형태의 응답을 받아야 한다.

**Why this priority**: 실시간 계층(Part B)에서는 같은 방 상태 정보를 REST 응답과 SSE/WebSocket 브로드캐스트 두 경로로 동시에 내보내야 한다. 두 경로가 같은 응답 형태를 공유하려면, 지금부터 API 계층이 내부 구현과 분리되어 있어야 나중에 브로드캐스트 경로를 추가하기 쉽다.

**Independent Test**: 게임방 생성/입장/준비/시작 API의 응답 구조가, 서버 내부 데이터 구조가 어떻게 바뀌든 동일한 필드 구성을 유지하는지 코드 검토로 확인하는 것만으로 독립적으로 검증할 수 있다(외부에서 관찰 가능한 동작은 기존과 동일해야 한다).

**Acceptance Scenarios**:

1. **Given** 게임방 생성/입장/준비/시작 API, **When** 각각을 호출하면, **Then** 이전과 동일한 필드 구성의 응답을 받는다(동작 변화 없음, 내부 구조만 정리됨).

---

### User Story 7 - 프론트엔드 분리 배포를 위한 접근 허용 정책 (Priority: P7)

프론트엔드가 백엔드와 다른 출처(도메인)에서 서비스되어도, 허용된 출처의 요청만 정상적으로 API와 실시간 연결을 이용할 수 있어야 한다.

**Why this priority**: 실시간 계층(SSE/WebSocket)은 브라우저의 출처 제한 정책에 더 민감하다. 실시간 연결을 열기 전에 허용 출처 정책부터 명시적으로 정해두어야 한다.

**Independent Test**: 허용 목록에 있는 출처와 없는 출처에서 각각 API를 호출했을 때, 허용된 출처만 정상 응답을 받고 그렇지 않은 출처는 브라우저 단에서 차단되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 허용 목록에 등록된 출처, **When** 그 출처에서 API를 호출하면, **Then** 정상적으로 응답을 받는다.
2. **Given** 허용 목록에 없는 출처, **When** 그 출처에서 API를 호출하면, **Then** 브라우저가 응답 접근을 차단한다.
3. **Given** 운영 환경이 바뀌어 허용해야 할 출처가 늘어난 상황, **When** 허용 목록 설정을 변경하면, **Then** 코드 변경 없이 반영된다.

---

### User Story 8 - 실시간 연결 전용 단기 인증 티켓 발급 (Priority: P8)

로그인한 사용자는 실시간 연결(로비 SSE 또는 방 내 WebSocket)을 열기 직전에, 그 연결 한 번에만 쓸 수 있는 단기 인증 티켓을 발급받을 수 있어야 한다.

**Why this priority**: 브라우저의 실시간 연결 방식(EventSource, 표준 WebSocket API 모두)은 커스텀 인증 헤더를 실어보낼 수 없어, 기존 인증 토큰을 그대로 주소창에 노출할 수 없다. 로비 SSE뿐 아니라 방 내 WebSocket도 동일한 제약을 받으므로, 실시간 계층(Part B) 전체를 시작하기 전 마지막 선행 조건으로 이 발급 기능이 먼저 갖춰져야 한다.

**Independent Test**: 로그인한 사용자가 티켓 발급을 요청해 받은 값으로 실시간 연결을 열면 성공하고, 같은 값으로 두 번째 연결을 시도하거나 유효 시간이 지난 뒤 사용하면 거부되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 실시간 연결용 단기 티켓 발급을 요청하면, **Then** 짧은 유효 시간을 가진 1회용 티켓을 받는다.
2. **Given** 발급받은 티켓, **When** 그 티켓으로 실시간 연결을 시도하면, **Then** 연결이 수락된다.
3. **Given** 이미 한 번 사용된 티켓, **When** 그 티켓으로 다시 연결을 시도하면, **Then** 연결이 거부된다.
4. **Given** 유효 시간이 지난 티켓, **When** 그 티켓으로 연결을 시도하면, **Then** 연결이 거부된다.

---

### User Story 9 - 대기 중인 게임방 목록을 실시간으로 조회 (Priority: P9)

누군가와 바로 게임하고 싶은 사용자는, 현재 대기 중인 게임방 목록을 별도로 새로고침하지 않아도 실시간으로 확인할 수 있어야 한다.

**Why this priority**: Part A(선행 작업) 완료 후 실시간 계층에서 가장 먼저 가치를 주는 기능이며, 이후 모든 실시간 브로드캐스트(입장, 나가기, 시작 등)가 이 목록 갱신 메커니즘을 공유한다.

**Independent Test**: 클라이언트가 로비 실시간 연결을 연 상태에서, 다른 클라이언트가 방을 생성/입장/나가기/시작하면 폴링 없이 목록이 즉시 갱신되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로비 실시간 연결을 새로 연 사용자, **When** 연결이 수립되면, **Then** 현재 대기 중인 방 목록과 각 방의 인원수·정원·상태를 즉시 받는다.
2. **Given** 로비 실시간 연결을 유지 중인 사용자, **When** 다른 사용자가 방을 생성하거나 기존 방에 입장/퇴장하면, **Then** 새로고침 없이 변경된 목록(또는 변경분)을 즉시 받는다.
3. **Given** 대기 중이던 방이 진행 중 상태로 전환된 상황, **When** 전환이 일어나면, **Then** 그 방은 목록에서 즉시 사라진다.
4. **Given** 실시간 연결이 일시적으로 끊긴 사용자, **When** 연결이 자동으로 재수립되면, **Then** 최신 목록을 다시 받는다.
5. **Given** 실시간 연결을 더 이상 사용하지 않는 상황(탭 종료, 타임아웃, 오류), **When** 연결이 종료되면, **Then** 서버는 더 이상 존재하지 않는 연결에 자원을 낭비하지 않고 정리한다.

### User Story 10 - 방 입장 시 현재 인원 상태를 실시간 기준으로 확인 (Priority: P9)

게임방에 코드나 링크로 입장하려는 사용자는, 입장 시도 응답에서 그 순간의 실제 인원수·정원·방 상태를 확인할 수 있어야 한다.

**Why this priority**: User Story 9(로비 실시간 목록)와 동일한 실시간 인원 관리 기반을 공유하므로 함께 완성되어야 한다.

**Independent Test**: 방에 입장을 시도했을 때 응답에 현재 인원/정원/상태가 함께 내려오고, 정원이 찼거나 이미 진행 중인 방에는 그 사유와 함께 입장이 거부되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 코드 또는 링크로 입장을 시도한 사용자, **When** 입장 요청이 처리되면, **Then** 응답에 현재 인원수/정원/방 상태가 함께 포함된다.
2. **Given** 이미 정원이 찼거나 진행 중/종료된 방, **When** 입장을 시도하면, **Then** 입장이 거부되고 그 사유(정원 초과 또는 진행 상태)가 함께 안내된다.

### User Story 11 - 연결이 끊겨도 바로 퇴장 처리되지 않고 유예 시간을 둠 (Priority: P10)

게임방에 참가한 사용자는, 명시적으로 나가기를 누르면 즉시 방을 나가지만, 새로고침이나 일시적인 네트워크 단절로 연결이 끊긴 경우에는 짧은 유예 시간 동안 자리를 지켜주길 원한다.

**Why this priority**: 실시간 로비 목록(User Story 9)이 갖춰진 다음에야 "누가 실제로 남아있는지"를 실시간으로 추적할 수 있고, 그 위에서만 유예 시간과 재접속 판정이 의미를 갖는다.

**Independent Test**: 방 참가자의 연결이 예기치 않게 끊긴 뒤 유예 시간 안에 같은 사용자로 같은 방에 재접속하면 퇴장 처리가 취소되고, 유예 시간을 넘기면 실제 퇴장(및 필요 시 방장 위임/방 종료)으로 처리되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방에 참가 중인 사용자, **When** "나가기"를 명시적으로 요청하면, **Then** 즉시 퇴장 처리되고 같은 방에 남아있는 다른 참가자는 그 사실(방장 위임 결과 포함)을 실시간으로 통보받는다.
2. **Given** 방에 참가 중인 사용자, **When** 실시간 연결이 예기치 않게 끊기면, **Then** 정해진 유예 시간(5~10초) 동안은 아직 퇴장 처리되지 않는다.
3. **Given** 유예 시간이 진행 중인 사용자, **When** 유예 시간 안에 같은 방으로 다시 접속하면, **Then** 퇴장 처리가 취소되고 방에 계속 남아있는 것으로 인정된다.
4. **Given** 유예 시간이 진행 중인 사용자, **When** 유예 시간 안에 재접속하지 못하면, **Then** 그 시점에 실제 퇴장으로 처리된다(방장이었다면 위임, 마지막 인원이었다면 방 종료).
5. **Given** 대기 중인 방에 이미 참가 중인 사용자, **When** 같은 방에 다시 입장을 시도하면(새로고침, 다른 탭 등), **Then** 인원수가 추가로 늘지 않고 기존 참가자로 인식되며, 진행 중이던 퇴장 유예 시간이 있었다면 취소된다.
6. **Given** 같은 방의 다른 참가자, **When** 상대방의 연결이 끊겨 유예 시간이 시작되면, **Then** "연결 끊김/재접속 대기 중" 상태를 실시간으로 통보받는다.
7. **Given** 유예 시간 중임을 통보받은 참가자, **When** 상대방이 유예 시간 안에 재접속에 성공하거나 반대로 실패해 실제 퇴장이 확정되면, **Then** 그 결과를 각각 실시간으로 통보받는다.

### User Story 12 - 게임 시작/종료 시점이 실시간으로 전파됨 (Priority: P11)

게임방에 참가한 두 사용자는, 둘 다 준비를 마치고 시작이 확정되는 순간을 실시간으로 통보받아야 하며, 시작된 방은 다른 사용자들이 보는 로비 목록에서 즉시 사라져야 한다.

**Why this priority**: 시작 가능 여부 판정과 상태 전환 로직 자체는 이미 구현되어 있으므로(001-backend-crud-api), 이 스토리는 그 전환 시점에 실시간으로 신호를 전파하는 부분만 추가한다.

**Independent Test**: 두 참가자가 모두 준비를 마치고 시작 요청이 성공했을 때, 방 안의 두 사용자에게 시작 사실이 실시간으로 전달되고, 동시에 로비 목록에서 그 방이 사라지는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 두 참가자 모두 준비를 마친 방, **When** 방장이 시작을 요청해 성공하면, **Then** 방 안의 두 참가자 모두 실시간으로 시작 사실을 통보받는다.
2. **Given** 방금 시작된 방, **When** 로비 실시간 목록을 보고 있는 다른 사용자들 화면을 확인하면, **Then** 그 방은 더 이상 목록에 보이지 않는다.

### User Story 13 - 실시간 연결은 로그인/방 참가자 확인을 통과해야만 열림 (Priority: P12)

서비스 운영자 입장에서, 로비 실시간 연결과 방 내 실시간 연결 모두 인증된 사용자만, 그리고 방 내 연결은 그 방의 실제 참가자만 열 수 있어야 한다.

**Why this priority**: User Story 9(로비)와 User Story 11/12(방 내 실시간)가 구현된 뒤에 그 위에 접근 제어를 얹는 것이 자연스러우며, 이후 시그널링 기능(User Story 14)도 동일한 접근 제어를 재사용한다.

**Independent Test**: 인증 정보 없이 또는 방에 속하지 않은 사용자로 각 실시간 연결을 시도했을 때 연결 자체가 거부되는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 유효한 단기 티켓이 없는 요청, **When** 로비 실시간 연결을 시도하면, **Then** 연결이 거부된다.
2. **Given** 유효한 인증 정보를 가졌지만 해당 방의 참가자가 아닌 사용자, **When** 그 방의 실시간 연결을 시도하면, **Then** 연결이 거부된다.
3. **Given** 해당 방의 실제 참가자, **When** 그 방의 실시간 연결을 시도하면, **Then** 연결이 수락된다.

### User Story 14 - 영상 통화 연결을 위한 신호 중계 (Priority: P13)

1:1 대전에 참가한 사용자는, 게임 중 상대방과 영상으로 연결되어 실시간으로 서로의 동작을 볼 수 있어야 한다. 실제 영상/음성 데이터는 두 브라우저가 직접 주고받으며, 서버는 연결을 맺기 위한 초기 신호만 중계한다.

**Why this priority**: 접근 제어(User Story 13)가 갖춰진 다음에 적용해야 같은 방이 아닌 사용자의 신호를 가로채는 문제를 막을 수 있어, 실시간 계층의 마지막 순서로 둔다.

**Independent Test**: 같은 방의 두 사용자 사이에서 연결 신호를 주고받았을 때 서로에게 정상 전달되고, 다른 방에 있는 사용자에게는 그 신호가 전혀 전달되지 않는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 같은 방에 참가 중인 두 사용자, **When** 한쪽이 영상 통화 연결 신호를 보내면, **Then** 같은 방의 상대방에게만 그 신호가 그대로(가공 없이) 전달된다.
2. **Given** 서로 다른 방에 참가 중인 사용자들, **When** 한 방에서 신호가 발생하면, **Then** 다른 방의 참가자에게는 전달되지 않는다.
3. **Given** 영상 통화 연결을 시도하는 사용자, **When** 연결 정보가 필요하면, **Then** 서버로부터 중계 서버 접속 정보를 받을 수 있다.

### User Story 15 - 방 생성/입장 후 실시간 연결을 확립하지 않으면 자동으로 방치가 정리됨 (Priority: P14)

서비스 운영자 입장에서, REST로 방을 생성하거나 입장한 뒤 정해진 시간 안에 방 내 실시간 연결(WebSocket)을 열지 않는 사용자(호스트든 게스트든)는, 자리를 영구적으로 차지하지 않고 자동으로 정리되어야 한다.

**Why this priority**: 이 동작은 방 내 실시간 연결 인증(User Story 13)과 나가기 재사용 로직(User Story 11)이 모두 갖춰진 뒤에야 구현할 수 있다 — 확정 전 참가자를 추적하는 방식과 확정 대기 시간 만료 시 처리 방식이 유예 시간(User Story 11)과 동일한 메커니즘을 재사용하기 때문에, 실시간 계층 중 가장 마지막에 둔다.

**Independent Test**: 사용자가 방을 생성하거나 입장한 뒤 방 내 WebSocket을 한 번도 열지 않고 설정된 시간(15초)을 넘기면, 호스트였던 경우 게스트가 있으면 위임되고 없으면 방이 종료되며, 게스트였던 경우 자리가 비워지는지 확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 방금 방을 생성한 사용자(호스트), **When** 15초 안에 그 방의 WebSocket 연결을 열지 않으면, **Then** 다른 참가자가 없으므로 방이 자동으로 종료(CLOSED)된다.
2. **Given** 호스트가 있는 방에 방금 입장한 사용자(게스트), **When** 15초 안에 그 방의 WebSocket 연결을 열지 않으면, **Then** 게스트 자리가 자동으로 비워져 다른 사용자가 입장할 수 있게 된다.
3. **Given** 호스트와 게스트가 모두 있는 방에서 호스트가 15초 안에 WebSocket을 열지 않은 상황, **When** 확인 대기 시간이 만료되면, **Then** 게스트가 있으므로(연결 여부와 무관) 방장 권한이 위임되고 방은 종료되지 않는다.
4. **Given** 방을 생성/입장한 직후의 사용자, **When** 15초 안에 방 내 WebSocket 연결을 성공적으로 열면, **Then** 확인 대기가 취소되고 정상적으로 방에 남는다.
5. **Given** 확인 대기 중인 참가자, **When** 로비 실시간 목록이나 다른 사용자의 입장 시도에서 그 방의 인원수를 조회하면, **Then** 확인 대기 여부와 무관하게 실제로 자리를 차지하고 있는 것으로(정원 계산에 포함되어) 표시된다.

### Edge Cases

- 선행 작업(Part A)이 끝나기 전에 실시간 계층(Part B) 관련 요청이 들어오면 어떻게 되는가? → 이번 스펙의 순서 제약이므로, 구현 착수 순서 문제이지 런타임 동작 문제는 아니다. Part B 관련 엔드포인트/연결은 Part A 완료 전에는 아예 존재하지 않아야 한다.
- 같은 사용자가 여러 탭에서 동시에 같은 방의 실시간 연결을 열면 어떻게 되는가? → 가장 최근 연결을 유효한 것으로 간주하고, 서버가 이전 연결을 명시적으로 종료한 뒤 최신 연결로 교체한다(User Story 11의 "세션 참조 교체"와 동일한 원칙 — "자연스럽게 정리"가 아니라 서버가 직접 닫는다).
- 유예 시간 안에 재접속했지만 다른 사용자가 이미 그 자리에 새로 입장한 경우는? → 방 정원 관리 규칙상 유예 시간 동안은 자리가 비어있지 않은 것으로 간주되므로, 다른 사용자의 신규 입장 자체가 애초에 허용되지 않는다.
- 실시간 티켓을 발급만 받고 실제로 연결에 쓰지 않으면 어떻게 되는가? → 유효 시간이 지나면 자동으로 만료되어 이후 어떤 연결 시도에도 사용할 수 없다.
- 방장이 유예 시간 중(아직 퇴장 확정 전)일 때 남은 참가자가 시작을 요청하면? → 방장 자리가 아직 확정적으로 비지 않았으므로(User Story 11 유예 정책과 동일), 위임이 완료되기 전까지는 기존 방장 기준으로 시작 가능 여부를 판단한다.
- 영상 통화 연결 신호 중계 중 상대방이 이미 방을 나간 상태라면? → 더 이상 그 방에 참가자로 존재하지 않으므로 신호가 전달될 대상이 없고, 이는 오류가 아니라 정상적인 방 종료 흐름의 일부로 처리된다.
- 종료(CLOSED) 상태로 전환된 지 오래되어 정리(삭제) 작업 대상이 된 방은, 삭제되는 시점에 로비 실시간 목록 구독자에게 별도 브로드캐스트가 필요한가? → 필요 없다. FR-011에 따라 그 방은 이미 진행 중/종료로 전환되는 즉시 실시간 목록에서 제거된 상태이므로, 그 이후 정리 작업이 실제로 데이터를 삭제하는 시점은 목록에 아무 영향을 주지 않는다. 정리 작업이 이미 목록에서 빠진 방만 정상적으로 대상으로 삼는지 검증하는 것으로 충분하다.
- 서버가 재시작되어 인메모리 실시간 상태가 전부 사라진 직후, DB에는 여전히 WAITING/IN_PROGRESS로 남아있던 방이 있다면? → FR-028에 따라 서버 시작 시점에 그런 방은 모두 CLOSED로 강제 전환되므로, 재시작 이후에는 실시간 상태와 DB 상태가 다시 일치한 채로 시작한다(좀비 방 없음).
- 호스트와 게스트가 둘 다 확인 대기 중(WebSocket을 아직 아무도 열지 않은) 상태에서 호스트의 확인 대기 시간이 먼저 만료되면? → FR-018 위임 규칙을 그대로 따른다 — 게스트가 실시간 연결을 확립했는지 여부와 무관하게 게스트가 존재하기만 하면(DB상 `guestUserId`가 설정돼 있으면) 방장 권한이 위임되며, 위임된 게스트(신규 호스트)는 자신의 확인 대기 시간이 남아있다면 계속 그 안에 연결을 확립해야 한다.
- 확인 대기 중인 참가자가 대기 시간이 끝나기 전에 같은 방에 다시 `POST /join`을 호출하면(중복 클릭 등)? → FR-020(재입장 인식)에 따라 이미 참가자로 인식되어 정상 응답을 받을 뿐, 확인 대기 시간이 새로 연장되지는 않는다 — 그렇지 않으면 REST 호출만 반복해 무한정 자리를 차지하는 악용이 가능해지기 때문이다.
- 호스트가 방을 만들고 실시간 연결까지 확립한 뒤 상대를 계속 기다리기만 해서 방치된 WAITING 방 보관 기간(FR-004)을 넘기면? → FR-030에 따라 실시간 연결이 살아있는 한 정리 대상에서 제외된다 — 접속 중인 사용자의 방을 데이터베이스 갱신 시각만 보고 방치된 것으로 오판해 삭제하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**Part A — 선행 안정화 작업 (실시간 계층 착수 전 필수 완료)**

- **FR-001**: 시스템은 인증 실패(401)와 인가 실패(403) 시에도, 다른 모든 API 오류와 동일한 필드 구성의 오류 응답을 반환해야 한다.
- **FR-002**: 시스템은 같은 게임방에 대한 동시 변경 요청 중 하나만 반영하고, 나머지는 최신 데이터가 아니라는 사유로 명확히 거부해야 하며, 그 거부 응답도 FR-001과 동일한 오류 형식을 따라야 한다.
- **FR-003**: 시스템은 대기 중(WAITING)이 아닌 방에서의 준비 상태 변경 요청을 거부해야 한다.
- **FR-004**: 시스템은 이미 종료(CLOSED)된 방뿐 아니라, 설정된 보관 기간을 초과해 대기(WAITING) 상태로 방치된 방도 주기적으로 자동 정리해야 한다. 단, 진행 중(IN_PROGRESS)인 방은 어떤 경우에도 자동 정리 대상이 되지 않아야 한다. (Part A 시점에는 데이터베이스 갱신 시각만을 기준으로 판단한다 — 실시간 연결 유무를 반영하는 정교화는 FR-030 참고.)
- **FR-005**: 시스템의 여러 주기적 백그라운드 작업은 서로 독립적으로 실행되어, 한 작업의 지연이 다른 작업의 실행 주기에 영향을 주지 않아야 한다.
- **FR-006**: 게임방 관련 기능을 제공하는 서비스 계층은 클라이언트에게 노출되는 응답을 내부 데이터 표현과 분리된 안정적인 형태로 직접 만들어내야 하며, 이 변경으로 기존 API의 관찰 가능한 동작(요청/응답 계약)이 달라지지 않아야 한다.
- **FR-007**: 시스템은 허용된 출처 목록을 코드 변경 없이 설정으로 지정할 수 있어야 하며, 목록에 없는 출처의 요청에는 응답 접근을 허용하지 않아야 한다.
- **FR-008**: 로그인한 사용자는 실시간 연결 전용 단기 인증 티켓을 발급받을 수 있어야 하며, 그 티켓은 짧은 유효 시간을 가지고 1회 사용 후 즉시 무효화되어야 한다.

**Part B — 실시간 계층 (Part A 완료 후 진행)**

- **FR-009**: 사용자는 별도의 새로고침이나 반복 조회 없이, 현재 대기 중인 게임방 목록을 실시간으로 받아볼 수 있어야 한다.
- **FR-010**: 방 생성, 입장, 퇴장, 방장 위임, 인원 변경, 상태 전환(시작, 종료) 등 목록에 영향을 주는 변경이 발생하면, 로비 목록을 실시간으로 구독 중인 모든 사용자에게 즉시 변경 사항이 전달되어야 한다.
- **FR-011**: 방이 진행 중 또는 종료 상태로 전환되면 그 즉시 실시간 목록에서 사라져야 한다.
- **FR-012**: 실시간 목록의 각 방에는 그 순간의 실제 인원수와 상태가 함께 제공되어야 한다.
- **FR-013**: 실시간 연결이 끊긴 클라이언트는 자동으로 재연결을 시도할 수 있어야 하며, 재연결 시 최신 목록을 다시 받아야 한다.
- **FR-014**: 더 이상 유효하지 않은 실시간 연결(종료/타임아웃/오류)은 서버 자원에서 정리되어야 한다.
- **FR-015**: 코드 또는 링크로 방 입장을 요청하면, 그 응답에 그 순간의 실제 인원수/정원/방 상태가 함께 포함되어야 한다.
- **FR-016**: 참가자는 명시적으로 나가기를 요청하면 즉시 퇴장 처리되어야 하며, 같은 방에 남아있는 다른 참가자에게 그 사실(방장 위임이 함께 일어났다면 그 결과 포함)이 실시간으로 전달되어야 한다.
- **FR-017**: 참가자의 실시간 연결이 예기치 않게 끊긴 경우, 즉시 퇴장 처리하지 않고 5~10초의 유예 시간을 두어야 하며, 그 안에 같은 사용자가 같은 방에 재접속하면 퇴장이 취소되어야 한다.
- **FR-018**: 유예 시간을 넘기면 그 시점에 실제 퇴장으로 처리되어야 하며, 대기 중인 방에서 방장이 이렇게 퇴장하면 기존 위임 규칙이 그대로 적용되어야 한다.
- **FR-019**: 참가자의 연결 끊김으로 유예 시간이 시작되면, 같은 방의 다른 참가자에게 그 사실("연결 끊김/재접속 대기 중")이 즉시 실시간으로 전달되어야 하며, 그 이후 재접속 성공 또는 유예 시간 만료로 인한 실제 퇴장 확정 결과도 각각 실시간으로 전달되어야 한다.
- **FR-020**: 대기 중인 방에 이미 참가 중인 사용자가 같은 방에 다시 입장을 시도하면, 인원수를 추가로 늘리지 않고 기존 참가자로 인식하며 최신 연결 참조로 교체되어야 한다. 진행 중이던 퇴장 유예 시간이 있었다면 취소되어야 한다.
- **FR-021**: 게임 시작이 확정되면, 방 안의 참가자들에게 실시간으로 시작 사실이 전달되어야 한다.
- **FR-022**: 게임이 시작되면 그 방은 로비 실시간 목록에서 즉시 제거되어야 한다.
- **FR-023**: 로비 실시간 연결은 유효한 단기 인증 티켓 없이는 열릴 수 없어야 한다.
- **FR-024**: 방 내 실시간 연결도 로비 실시간 연결(FR-023)과 마찬가지로 유효한 단기 인증 티켓 없이는 열릴 수 없어야 하며, 추가로 요청한 사용자가 그 방의 실제 참가자인 경우에만 열릴 수 있어야 한다. 연결이 열린 이후에도 메시지를 주고받을 때마다 그 사용자가 여전히 해당 방의 참가자인지 검증해야 한다(참가자가 아니게 된 이후의 메시지는 차단된다).
- **FR-025**: 같은 방에 참가 중인 두 사용자는 영상 통화 연결을 위한 신호(연결 제안/응답/후보 경로 정보)를 서버를 통해 서로 주고받을 수 있어야 하며, 서버는 그 신호의 내용을 가공하지 않고 그대로 전달해야 한다.
- **FR-026**: 서로 다른 방에 속한 사용자 사이에는 영상 통화 연결 신호가 전달되지 않아야 한다.
- **FR-027**: 영상 통화 연결을 시도하는 사용자는 중계 서버 접속 정보를 제공받을 수 있어야 한다.
- **FR-028**: 서버가 시작될 때, 직전 재시작으로 인해 인메모리 실시간 상태 없이 대기(WAITING) 또는 진행 중(IN_PROGRESS) 상태로 남아있는 방은 모두 종료(CLOSED)로 강제 전환되어야 한다(재시작 전 상태를 신뢰할 수 없으므로).
- **FR-029**: 방 생성 또는 입장으로 참가자(호스트 또는 게스트)가 확정된 직후, 설정된 시간(15초) 안에 그 참가자가 해당 방의 실시간 연결(WebSocket)을 확립하지 못하면 시스템은 자동으로 그 참가자를 퇴장 처리해야 하며, 이 퇴장 처리는 기존 나가기 규칙(FR-018, 호스트면 위임 또는 방 종료, 게스트면 자리 비움)을 동일하게 따라야 한다. 확인 대기 중인 참가자도 그 시간 동안은 정원 계산과 실시간 목록의 인원수에 그대로 포함된다.
- **FR-030**: FR-004의 방치된 WAITING 방 자동 정리는, 실시간 연결이 확립된 참가자가 실제로 남아있는 방은(비록 데이터베이스 보관 기간 기준을 넘겼더라도) 정리 대상에서 제외해야 한다 — 실시간 계층 도입 이후에는 데이터베이스 갱신 시각만으로 "방치 여부"를 판단할 수 없기 때문이다.

### Out of Scope (이번 스펙 제외 범위)

- 게임방 생성/입장/나가기/준비/시작/결과보고 REST API의 **엔드포인트 계약(요청/응답 형식)과 핵심 상태 전이 규칙(WAITING/IN_PROGRESS/CLOSED 전이 자체)**은 001-backend-crud-api에서 이미 완료된 범위로 다시 다루지 않는다. 단, 그 구현 내부에는 이번 스펙의 실시간 계층을 지원하기 위한 수정이 들어간다 — `join()`의 재입장 인식 보강(FR-020, 001에 있던 결함 수정), `create()`/`join()`의 확인 대기 타이머 등록(FR-029), `leave()`의 실시간 브로드캐스트 트리거(FR-016) — 이들은 외부에 노출되는 REST 계약 자체를 바꾸는 것이 아니라 기존 계약을 그대로 둔 채 내부 동작을 보강하는 것이라 이 Out of Scope 항목과 상충하지 않는다.
- CLOSED 상태 방에 대한 기본 자동 정리 동작 자체(001-backend-crud-api에서 이미 완료 — 이번 스펙에서는 대상 범위를 WAITING까지 넓히는 부분(FR-004)과, 실시간 연결이 살아있는 WAITING 방을 정리 대상에서 제외하는 부분(FR-030)만 추가로 다룬다).
- 게임 결과 저장 성공 후 성장(펫 경험치) 모듈에 결과를 알리는 부분(기존 지라 GAME-02-08의 `GameWonEvent` 발행 등) — 실시간 계층(SSE/WebSocket)과 무관한 후처리이므로 이번 스펙에서 제외하며, 필요 시 별도 스펙에서 다룬다.
- 실시간 연결 이후 실제로 주고받는 게임 진행 메시지(문제 배포, 정답 판정, 점수/콤보 계산 등)의 내용과 형식 — 별도 담당자가 이어서 구현할 영역이며, 이 스펙은 "그 메시지가 실려 나갈 수 있는 실시간 연결 자체를 여는 지점까지"만 다룬다.
- STUN/TURN 중계 서버 자체의 구축/운영(인프라 영역) — 이 스펙은 그 접속 정보를 클라이언트에 전달하는 부분까지만 다룬다.
- 다중 인스턴스 확장, Redis 등을 이용한 인스턴스 간 상태 공유 — 단일 인스턴스 운영을 전제로 한다.

### Key Entities *(include if feature involves data)*

- **오류 응답(Error Response)**: 모든 API 오류(비즈니스 오류, 인증/인가 오류 포함)가 공통으로 따르는 응답 형태.
- **실시간 인증 티켓(Realtime Ticket)**: 로그인한 사용자에게 발급되는, 짧은 유효 시간과 1회성을 가진 실시간 연결 전용 자격 증명.
- **로비 구독(Lobby Subscription)**: 대기 중인 게임방 목록을 실시간으로 받아보기 위해 클라이언트가 맺는 연결. 유효하지 않게 되면 서버에서 정리된다.
- **실시간 참가자 상태(Live Room Membership)**: 게임방별로 그 순간 실제로 접속해 있는 참가자, 각자의 준비 상태, 실시간 연결 확정 여부(방 생성/입장 직후에는 미확정 상태로 시작해 WebSocket 연결이 처음 성공하는 순간 확정된다, FR-029), 진행 중인 퇴장 유예 또는 확인 대기 여부(연결 끊김/재접속 대기 중 여부는 같은 방의 다른 참가자에게도 실시간으로 노출된다)를 나타내는 휘발성 상태(방이 삭제되거나 서버가 재시작되면 사라지는 성격 — 재시작 시의 복구는 FR-028 참고).
- **시그널 메시지(Signal Message)**: 같은 방의 두 참가자 사이에서 오가는, 서버가 내용을 해석하지 않고 그대로 전달하는 영상 통화 연결용 메시지.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Part A의 6개 선행 항목(FR-001~FR-006)과 CORS/티켓 발급(FR-007~FR-008)이 모두 완료되어 각각의 인수 시나리오를 100% 통과하기 전에는, Part B의 어떤 실시간 엔드포인트도 존재하지 않는다.
- **SC-002**: 로비 목록을 구독 중인 사용자는 다른 사용자의 방 생성/입장/퇴장/시작이 일어난 시점으로부터 3초 이내에 목록 변화를 확인할 수 있다(별도 새로고침 불필요).
- **SC-003**: 연결이 예기치 않게 끊긴 사용자가 유예 시간 안에 재접속하면 100% 퇴장 처리가 취소되며, 유예 시간을 넘긴 경우 100% 실제 퇴장으로 처리된다.
- **SC-004**: 인증되지 않았거나 해당 방의 참가자가 아닌 요청의 실시간 연결 시도는 100% 거부된다.
- **SC-005**: 같은 방의 두 참가자 사이에서 오간 영상 통화 연결 신호는 100% 서로에게 전달되고, 다른 방 참가자에게는 0% 전달된다.
- **SC-006**: 동시 변경 요청 충돌 상황에서 두 요청이 모두 성공한 것처럼 보이는 사례가 0건이다(데이터 유실 없음).
- **SC-007**: 방을 생성/입장한 뒤 실시간 연결을 한 번도 열지 않은 참가자는 100% 15초 이내에 자동으로 정리되어, 방치로 인해 정원을 영구 점유하는 사례가 0건이다.
- **SC-008**: 실시간 연결이 살아있는 참가자가 있는 WAITING 방은, 데이터베이스 보관 기간 경과 여부와 무관하게 0%의 확률로 자동 정리(삭제)된다.

## Assumptions

- 001-backend-crud-api에서 이미 구현된 게임방 REST API(생성/입장/나가기/준비/시작/결과보고)와 CLOSED 방 정리 스케줄러의 기본 동작은 그대로 재사용하며, 이 스펙은 그 위에 실시간 계층과 결함 수정만 추가한다.
- 단일 인스턴스 운영을 전제로 하므로, 로비 구독자 목록과 방별 실시간 참가자 상태는 인스턴스 메모리 내에서만 관리하면 충분하고, 인스턴스 간 상태 동기화(Redis Pub/Sub 등)는 필요하지 않다. 다만 이 메모리 상태는 서버 재시작 시 사라지므로, 재시작 직후에는 FR-028에 따른 시동 정리로 DB 상태를 신뢰 가능한 상태로 되돌린다.
- 배포 환경은 Nginx를 프록시로 사용하며, 실시간 목록 연결 응답은 프록시 버퍼링에 의해 지연되지 않아야 한다(응답 헤더 수준의 설정으로 해결 가능하다고 가정).
- 로비 SSE(`EventSource`)와 방 내 WebSocket(브라우저 표준 `WebSocket` API) 모두 브라우저 표준 기능으로 여는 방식이며, 둘 다 커스텀 인증 헤더를 실어보낼 수 없다는 동일한 제약이 있어(WebSocket도 예외가 아니다) 두 연결 모두 동일하게 단기 티켓을 쿼리 파라미터로 전달하는 방식을 채택했다. `wscat`/Postman 같은 CLI 도구는 핸드셰이크 시 커스텀 헤더를 보낼 수 있어 개발 중 혼동하기 쉬우나, 실제 브라우저 클라이언트 기준으로 결정한다.
- 로비 SSE는 브라우저 `EventSource` API의 특성상 연결 실패 시 `onerror`만 발생하고 HTTP 상태 코드나 응답 바디(오류 사유)를 클라이언트 코드에서 읽을 수 없다. 따라서 클라이언트는 오류 발생 시 응답 바디를 파싱하려 하지 말고, 곧바로 새 티켓을 재발급받아 재연결을 시도해야 한다(티켓은 1회성이라 `EventSource`의 기본 자동 재연결이 같은 티켓으로 재시도하면 항상 실패하므로, 자동 재연결에 의존하지 않고 애플리케이션 코드가 재발급까지 담당해야 한다).
- 방 내 실시간 연결(입장/퇴장 유예, 게임 시작 알림, 영상 통화 신호 중계)은 양방향 연결 방식으로 열리며, 연결을 맺는 시점의 인증/권한 검증까지만 이 스펙의 책임이다. 연결이 열린 이후 오가는 실제 게임 진행 메시지의 내용/형식은 별도 담당자 영역으로 남겨둔다.
- 유예 시간(5~10초), 티켓 유효 시간, 방치된 WAITING 방의 보관 기간, 실시간 목록 재전송 주기 등 구체적인 수치는 운영 중 조정 가능한 설정값으로 두며, 정확한 기본값 확정은 계획(plan) 단계에서 다룬다.
- FR-028은 대기(WAITING) 방과 진행 중(IN_PROGRESS) 방을 구분하지 않고 서버 재시작 시 모두 강제 종료한다. 실시간 1:1 대전 특성상 진행 중인 게임을 그대로 유지한 채 무중단으로 재배포하는 것은 실질적으로 어렵다고 보고, 재시작 시점에 진행 중이던 대전은 결과 미저장으로 소실되는 것을 감수하기로 결정했다(001 스펙 FR-023의 "즉시 나가기로 인한 무효화"와 동일한 취급).
- 영상 통화의 중계 서버(STUN/TURN) 자체는 별도 인프라로 이미 준비되거나 준비될 것으로 가정하며, 이 스펙은 그 접속 정보를 전달하는 책임만 진다.
- FR-029의 실시간 연결 확인 대기 시간은 15초로 하며(퇴장 유예 시간 5~10초보다 여유를 둔 값 — 티켓 발급, 페이지 로딩, WebSocket 핸드셰이크에 걸리는 시간을 감안), 호스트와 게스트 모두에게 동일하게 적용한다. 이 기능은 001에서 "REST로는 입장했지만 실제 연결은 하지 않는 사용자가 정원을 영구 점유하는 문제"로 예고됐던 것을 이번 스펙에서 실제로 해소하기로 결정한 것이며(당초에는 범위 밖으로 미루는 방향으로 검토됐으나, 완결성 있는 백엔드를 위해 이번 스펙에 포함하기로 변경), FR-029의 퇴장 처리는 새로운 로직이 아니라 FR-016~018(나가기/유예)과 동일한 처리 경로를 재사용한다.
