# Feature Specification: 백엔드 CRUD API 1차 구축

**Feature Branch**: `001-backend-crud-api`

**Created**: 2026-07-21

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - API 명세 문서를 가장 먼저 제공 (Priority: P1)

백엔드 개발을 담당하는 팀과, 이 API를 소비하는 프론트엔드/게임 파트 담당자는 어떤 도메인 API도 구현되기 전에 먼저 API 문서화 체계를 통해 엔드포인트 목록, 요청/응답 형식, 인증 요구사항을 확인하고 시험 호출까지 할 수 있어야 한다.

**Why this priority**: 이번 개발은 여러 도메인(회원/학습/테스트/게임/랭킹)의 API를 병렬로 다루므로, 문서화 체계를 가장 먼저 구축해두면 이후 추가되는 모든 API가 자동으로 문서에 반영되어 연동 담당자가 실제 구현 완료를 기다리지 않고 계약(contract) 기준으로 병행 작업할 수 있다. 팀 결정에 따라 다른 어떤 기능보다 먼저 착수한다.

**Independent Test**: 아직 실제 도메인 API가 하나도 구현되지 않은 상태에서, 문서화 체계와 인증 시험 호출(Authorize) 기능, 도메인별 그룹핑(Tag)만으로 독립적으로 구축·검증할 수 있다. 이후 임의의 API 한 개를 추가했을 때 별도 수작업 없이 문서에 자동 반영되는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 아직 다른 도메인 API 개발이 시작되지 않은 시점, **When** 백엔드 개발이 착수되면, **Then** API 문서화 체계가 가장 먼저 준비되어 이후 모든 API 구현의 기준(계약)이 된다.
2. **Given** 새로운 API 엔드포인트가 구현된 상황, **When** 문서 페이지를 열람하면, **Then** 해당 엔드포인트의 요청/응답 형식과 인증 필요 여부가 별도 수작업 없이 문서에 반영되어 있다.
3. **Given** 인증이 필요한 API, **When** 문서 페이지에서 인증 토큰을 입력하고 해당 API를 시험 호출하면, **Then** 실제 서버에 요청이 전달되고 응답 결과를 문서 화면에서 바로 확인할 수 있다.
4. **Given** 회원/학습/테스트/게임/랭킹 등 여러 도메인의 API가 섞여 있는 상황, **When** 문서 페이지를 열람하면, **Then** 도메인별로 그룹화되어 있어 원하는 API를 쉽게 찾을 수 있다.

### User Story 2 - 회원가입, 로그인, 계정 관리 (Priority: P2)

사용자는 이메일과 비밀번호로 회원가입하고, 로그인/로그아웃하며, 언제든 자신의 프로필을 조회·수정하고, 필요하면 탈퇴할 수 있다.

**Why this priority**: 문서화 체계 다음으로, 학습·테스트·게임·랭킹 등 나머지 모든 기능은 로그인한 사용자를 전제로 하므로 계정 시스템이 가장 먼저 완성되어야 하는 기능적 기반이다.

**Independent Test**: 회원가입 → 로그인(토큰 발급) → 프로필 조회/수정 → 로그아웃 → 재로그인 시도(차단 확인) → 회원 탈퇴 → 탈퇴 계정으로 로그인 시도(차단 확인) 흐름만으로 독립적으로 테스트하고 가치를 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 아직 가입하지 않은 사용자, **When** 이메일·비밀번호·닉네임으로 회원가입을 요청하면, **Then** 계정이 생성된다.
2. **Given** 이미 가입된 이메일, **When** 동일 이메일로 다시 회원가입을 시도하면, **Then** 가입이 거부되고 중복 사유가 안내된다.
3. **Given** 가입된 사용자, **When** 올바른 이메일·비밀번호로 로그인하면, **Then** 이후 요청에 사용할 인증 토큰과 재발급용 토큰을 받는다.
4. **Given** 로그인 상태의 사용자, **When** 재발급용 토큰으로 갱신을 요청하면, **Then** 유효 기간 내에서 새 인증 토큰을 받는다.
5. **Given** 로그인 상태의 사용자, **When** 로그아웃을 요청하면, **Then** 해당 재발급용 토큰은 더 이상 갱신에 사용할 수 없게 된다.
6. **Given** 로그인 상태의 사용자, **When** 닉네임/프로필 이미지를 수정하면, **Then** 변경된 값이 즉시 프로필 조회에 반영된다.
7. **Given** 로그인 상태의 사용자, **When** 회원 탈퇴를 요청하면, **Then** 계정은 즉시 비활성화(소프트 삭제)되고 이후 해당 자격 증명으로는 로그인할 수 없다.
8. **Given** 탈퇴한 사용자, **When** 탈퇴 전 사용하던 이메일로 다시 회원가입을 시도하면, **Then** 새 계정으로 가입이 허용된다.

### User Story 3 - 학습 콘텐츠 열람과 오답 관리 (Priority: P3)

사용자는 카테고리별 학습 콘텐츠(자음/모음/숫자/단어) 목록을 조회하고, 연습·테스트 중 틀린 문제를 신고하며, 카테고리별 최근 오답을 확인할 수 있다.

**Why this priority**: 학습 콘텐츠 조회와 오답 기록은 서비스의 핵심 학습 루프이며, 게임·랭킹 등 부가 기능보다 먼저 검증되어야 하는 본질 기능이다.

**Independent Test**: 로그인한 사용자가 특정 카테고리의 콘텐츠 목록을 조회 → 오답을 신고 → 해당 카테고리의 오답노트에서 방금 신고한 오답이 조회되는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 특정 카테고리(예: 자음)로 학습 콘텐츠 목록을 조회하면, **Then** 현재 노출 가능한(비활성 처리되지 않은) 콘텐츠만 반환된다.
2. **Given** 로그인한 사용자, **When** 특정 콘텐츠에 대해 오답을 신고하면, **Then** 오답 기록이 저장된다.
3. **Given** 특정 카테고리에 여러 번 오답을 신고한 사용자, **When** 해당 카테고리의 오답노트를 조회하면, **Then** 가장 최근 신고 순으로 최대 5건이 반환된다.
4. **Given** 오답을 한 번도 신고하지 않은 카테고리, **When** 해당 카테고리 오답노트를 조회하면, **Then** 빈 목록이 반환된다.
5. **Given** 로그인한 사용자, **When** 테스트를 마치고 총 문제 수와 정답 수를 보고하면, **Then** 해당 결과가 기록된다. (정답 수 기반 펫 경험치 반영은 이번 1차 범위에서 제외되며, "Out of Scope" 절 참고)

### User Story 4 - 게임방 생성·참가·진행 관리 (Priority: P4)

사용자는 1:1 대전용 게임방을 만들거나 코드로 참가하고, 준비 상태를 표시해 게임을 시작하며, 방을 나가거나 게임 결과가 안전하게 저장되는 것을 신뢰할 수 있다. (본 1차 목표에서는 실시간 목록 갱신·실시간 동기화 등 WebSocket/SSE 기반 기능은 다루지 않으며, 방 생성/참가/퇴장/준비/시작/결과 저장과 같은 CRUD성 동작만 대상으로 한다.)

**Why this priority**: 게임 매칭은 서비스의 핵심 참여 유도 기능이지만, 문서화 체계·계정·학습 기능이 먼저 갖춰져야 의미가 있어 4순위로 둔다. 실시간 갱신(SSE/WebSocket)은 이번 1차 범위에서 제외하고, 데이터 생성·조회·변경·삭제에 해당하는 부분만 우선 구현한다.

**Independent Test**: 사용자 A가 방을 생성 → 사용자 B가 발급된 코드로 입장 → 둘 다 준비 완료 표시 → 시작 요청 성공 → 게임 결과를 보고해 저장되고 각자의 승/패 기록이 갱신되는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 게임방 생성을 요청하면, **Then** 고유한 참가 코드가 발급된 방이 만들어지고 해당 사용자가 방장이 된다.
2. **Given** 유효한 참가 코드, **When** 다른 사용자가 그 코드로 입장을 요청하면, **Then** 정원 내에서 입장이 허용되고 현재 인원/정원/방 상태가 함께 안내된다.
3. **Given** 이미 정원이 찬 방, **When** 추가 사용자가 입장을 시도하면, **Then** 입장이 거부된다.
4. **Given** 진행 중(IN_PROGRESS)인 방, **When** 새로운 사용자가 그 방에 입장을 시도하면, **Then** 입장이 거부된다.
5. **Given** 대기 중(WAITING)인 방에 참가 중인 사용자(방장이 아님), **When** 명시적으로 방 나가기를 요청하면, **Then** 즉시 방에서 제외된다.
6. **Given** 대기 중(WAITING)인 방에서 방장이 나가고 다른 참가자가 남아있는 상황, **When** 방장이 나가기를 완료하면, **Then** 남은 참가자에게 방장 권한이 위임된다.
7. **Given** 진행 중(IN_PROGRESS)인 방에 참가 중인 사용자, **When** 명시적으로 방 나가기를 요청하면, **Then** 즉시 방 상태가 종료(CLOSED)로 전환되고 해당 게임은 무효 처리되어 결과가 저장되지 않는다(방장/참가자 구분 없이 동일하게 적용 — 위임 대상이 없으므로).
8. **Given** 방에 참가자가 한 명도 남지 않은 상황, **When** 마지막 참가자가 나가면, **Then** 방 상태가 종료(CLOSED)로 전환된다.
9. **Given** 종료(CLOSED) 상태로 전환된 지 5분이 지난 방, **When** 정리 작업이 실행되면, **Then** 해당 방 데이터는 자동으로 삭제되며 이미 저장된 게임 결과 기록에는 영향이 없다.
10. **Given** 방에 참가한 두 사용자, **When** 둘 다 준비 완료 상태로 표시하고 방장이 게임 시작을 요청하면, **Then** 방 상태가 진행 중으로 전환된다.
11. **Given** 참가자 중 한 명만 준비 완료한 상황, **When** 방장이 게임 시작을 요청하면, **Then** 시작 요청은 거부된다.
12. **Given** 진행 중이던 게임, **When** 최종 승자와 점수를 결과로 보고하면, **Then** 매치 결과가 저장되고 두 참가자의 승/패 횟수가 갱신되며 방 상태가 종료로 전환된다.
13. **Given** 이미 결과가 저장된 게임, **When** 동일한 결과 보고 요청이 중복으로 들어오면, **Then** 결과가 다시 반영되지 않고 기존 저장 상태가 유지된다.

### User Story 5 - 랭킹 조회 (Priority: P5)

사용자는 전체 사용자 중 승수 기준 상위 5명의 랭킹과 자신의 현재 순위를 확인할 수 있다.

**Why this priority**: 랭킹은 게임 결과 데이터가 쌓여야 의미가 생기는 부가 기능이라 게임 매칭보다 뒤에 둔다.

**Independent Test**: 승/패 기록이 있는 여러 사용자 계정으로 랭킹을 조회했을 때 승수 내림차순 상위 5명과 조회자 본인의 순위가 정확히 반환되는지 확인하는 것만으로 독립적으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 승/패 기록을 가진 여러 사용자, **When** 랭킹을 조회하면, **Then** 승수 기준 상위 5명이 내림차순으로 반환된다.
2. **Given** 승수가 동일한 사용자가 여러 명 있는 상황, **When** 랭킹을 조회하면, **Then** 패 수가 적은 순으로 순서가 결정된다.
3. **Given** 상위 5명에 들지 않는 사용자, **When** 랭킹을 조회하면, **Then** 상위 5명 목록과 함께 본인의 전체 순위가 별도로 표시된다.
4. **Given** 탈퇴한 사용자, **When** 랭킹을 조회하면, **Then** 탈퇴한 사용자는 목록과 순위 계산에서 제외된다.

### Edge Cases

- 존재하지 않는 참가 코드로 게임방 입장을 시도하면 어떻게 되는가? → 입장이 거부되고 유효하지 않은 코드임이 안내되어야 한다.
- 만료되었거나 이미 무효화된 재발급용 토큰으로 갱신을 요청하면 어떻게 되는가? → 갱신이 거부되고 재로그인이 필요함이 안내되어야 한다.
- 탈퇴한 사용자의 과거 게임 전적·랭킹 관련 데이터는 어떻게 되는가? → 개인 식별 정보(이메일 등)만 변형되고, 전적·게임 결과 데이터 자체는 보존되어야 한다(랭킹 집계에서는 제외).
- 게임방에 속하지 않은 사용자가 해당 방의 나가기/준비/시작/결과 API를 호출하면 어떻게 되는가? → 요청이 거부되어야 한다.
- 오답 신고 시 존재하지 않는 콘텐츠 ID를 전달하면 어떻게 되는가? → 요청이 거부되어야 한다.
- 자신이 참가하지 않은 게임의 결과를 보고하려 하면 어떻게 되는가? → 요청이 거부되어야 한다.
- 아직 문서화 체계가 반영되지 않은 API가 존재할 수 있는가? → 이번 1차 목표에서는 문서화 체계를 가장 먼저 구축하므로, 이후 구현되는 모든 도메인 API는 예외 없이 문서에 반영되어야 한다.
- 펫/출석체크 관련 화면이나 API 호출이 들어오면 어떻게 되는가? → 이번 1차 범위에는 해당 기능(API·비즈니스 로직)이 없으므로 제공되지 않으며, 이는 의도된 범위 제외임을 "Out of Scope" 절에서 확인할 수 있다.
- 사용자가 명시적으로 나가기를 요청하지 않고 방을 오랫동안 방치하면 어떻게 되는가? → 1차 범위(REST 전용)에서는 별도의 자동 정리 대상이 아니다. 서버가 계속 유지해야 하는 연결 상태가 없어 방치된 방이 다른 사용자에게 영향을 주지 않기 때문이며, 이는 "Out of Scope"에 명시된 대로 WebSocket 기반 실시간 기능 도입 시 함께 다룬다.

## Requirements *(mandatory)*

### Functional Requirements

**API 문서화 (최우선 진행)**

- **FR-001**: 시스템은 다른 도메인 API 구현에 앞서 API 문서화 체계를 가장 먼저 갖추어야 한다.
- **FR-002**: 시스템은 구현되는 각 API 엔드포인트에 대해 요청/응답 형식과 인증 요구사항을 문서에 반영해야 하며, 새 API가 추가될 때마다 별도 수작업 없이 최신 상태로 유지되어야 한다.
- **FR-003**: 문서화 체계는 인증이 필요한 API에 대해 인증 토큰을 입력한 뒤 문서 화면에서 바로 시험 호출할 수 있는 기능을 제공해야 한다.
- **FR-004**: 문서화 체계는 API를 도메인(회원/학습/테스트/게임/랭킹)별로 그룹화하여 보여주어야 한다.

**회원/인증**

- **FR-005**: 시스템은 이메일·비밀번호·닉네임으로 신규 회원가입을 허용해야 한다.
- **FR-006**: 시스템은 이미 사용 중인 이메일로의 중복 가입을 거부해야 한다.
- **FR-007**: 시스템은 등록된 이메일·비밀번호로 로그인을 허용하고, 인증 토큰과 재발급용 토큰을 발급해야 한다.
- **FR-008**: 시스템은 유효한 재발급용 토큰으로 인증 토큰 갱신을 허용해야 한다.
- **FR-009**: 시스템은 로그아웃 시 해당 재발급용 토큰을 더 이상 갱신에 사용할 수 없도록 무효화해야 한다.
- **FR-010**: 시스템은 탈퇴한 계정의 로그인 시도를 차단해야 한다.
- **FR-011**: 사용자는 자신의 프로필(닉네임, 프로필 이미지, 승/패 기록)을 조회할 수 있어야 한다.
- **FR-012**: 사용자는 자신의 닉네임과 프로필 이미지를 수정할 수 있어야 한다.
- **FR-013**: 사용자는 회원 탈퇴를 요청할 수 있어야 하며, 탈퇴 시 계정은 즉시 비활성화(소프트 삭제)되고 보유한 모든 재발급용 토큰이 함께 무효화되어야 한다.
- **FR-014**: 탈퇴 처리된 이메일은 원본 그대로 보존되지 않고 변형되어, 동일 이메일로 신규 가입이 가능해야 한다.

**학습 콘텐츠 / 테스트·오답노트**

- **FR-015**: 사용자는 카테고리(자음/모음/숫자/단어)별로 현재 노출 가능한 학습 콘텐츠 목록을 조회할 수 있어야 한다.
- **FR-016**: 사용자는 특정 학습 콘텐츠에 대한 오답을 신고할 수 있어야 하며, 신고 시점이 함께 기록되어야 한다.
- **FR-017**: 사용자는 카테고리별로 자신이 신고한 최근 오답 최대 5건을 최신순으로 조회할 수 있어야 한다.
- **FR-018**: 사용자는 테스트 종료 시 총 문제 수와 정답 수를 보고할 수 있어야 하며, 해당 결과가 저장되어야 한다. (정답 수에 따른 펫 경험치 반영·조회는 이번 범위에서 제외)

**게임방 매칭 (CRUD 범위)**

- **FR-019**: 사용자는 1:1 대전용 게임방을 생성할 수 있어야 하며, 생성 시 고유한 참가 코드가 발급되어야 한다.
- **FR-020**: 사용자는 발급된 참가 코드로 게임방에 입장할 수 있어야 하며, 정원이 찼거나 이미 진행 중인 방에는 입장할 수 없어야 한다.
- **FR-021**: 방 참가자는 명시적으로 방 나가기를 요청할 수 있어야 하며, 요청 즉시 처리되어야 한다. 단, 방이 진행 중(IN_PROGRESS)인 상태에서 나가기가 요청되면 인원 감소 처리 대신 즉시 게임이 무효화되어야 한다(FR-023).
- **FR-022**: 대기(WAITING) 상태의 방에서 방장이 나가고 다른 참가자가 남아있으면, 방장 권한이 남은 참가자에게 위임되어야 한다. (진행 중인 방에서의 나가기는 위임 대상이 없으므로 FR-023을 따른다.)
- **FR-023**: 방에 참가자가 더 이상 남지 않거나, 진행 중(IN_PROGRESS)인 방에서 참가자가 나가거나, 게임 결과 보고가 성공적으로 처리되면, 방 상태가 종료(CLOSED)로 전환되고 그 전환 시각이 기록되어야 한다. 진행 중인 방에서의 나가기로 인한 전환은 게임을 무효화하며 결과가 저장되지 않는다 — 명시적으로 나가지 않고 조용히 응답이 없어진 경우와 동일하게(둘 다 결과 미저장) 취급해, 나가기 버튼을 누르는 것이 불이익이 되지 않도록 한다.
- **FR-024**: 종료(CLOSED) 상태의 방은 전환 후 5분 이내에 자동으로 정리(삭제)되어야 하며, 이 정리 작업은 이미 저장된 게임 결과 데이터에 영향을 주지 않아야 한다.
- **FR-025**: 방 참가자는 자신의 준비 상태를 표시할 수 있어야 한다.
- **FR-026**: 방장은 모든 참가자가 준비 완료된 경우에만 게임 시작을 요청할 수 있어야 하며, 준비되지 않은 참가자가 있으면 시작 요청은 거부되어야 한다.
- **FR-027**: 게임 종료 후 최종 승자와 점수를 보고하면, 매치 결과가 저장되고 관련 참가자들의 승/패 기록이 갱신되어야 하며, 처리 완료 후 방 상태가 종료(CLOSED)로 전환되어야 한다.
- **FR-028**: 동일한 게임 결과가 중복으로 보고되어도 결과가 두 번 반영되지 않아야 한다(멱등 처리).
- **FR-029**: 게임 결과 저장은 방 데이터와 독립적으로 보존되어야 하며, 이후 방이 삭제되어도 결과 기록에는 영향이 없어야 한다.

**랭킹**

- **FR-030**: 사용자는 승수 기준 상위 5명의 랭킹을 조회할 수 있어야 한다.
- **FR-031**: 사용자는 상위 5명에 포함되지 않더라도 자신의 전체 순위를 함께 확인할 수 있어야 한다.
- **FR-032**: 승수가 동일한 사용자 간에는 패 수가 적은 사용자가 더 높은 순위를 가져야 한다.
- **FR-033**: 탈퇴한 사용자는 랭킹 목록과 순위 계산에서 제외되어야 한다.

**펫 / 출석 (데이터 구조 준비만)**

- **FR-034**: 시스템은 향후 성장 요소(펫) 기능 확장을 위해 사용자별 펫 데이터(이름, 레벨, 경험치)를 저장할 수 있는 데이터 구조를 준비해야 한다. 이번 1차 범위에서는 해당 데이터를 노출·변경하는 API나 경험치 증가·레벨업 로직은 제공하지 않는다.
- **FR-035**: 시스템은 향후 출석체크 기능 확장을 위해 사용자별 출석 데이터(날짜, 연속 출석 일수)를 저장할 수 있는 데이터 구조를 준비해야 한다. 이번 1차 범위에서는 출석 체크 API나 관련 로직은 제공하지 않는다.

### Out of Scope (1차 목표 제외 범위)

- 실시간 게임방 목록 구독(SSE) 및 실시간 인원/상태 브로드캐스트
- 게임 진행 중 실시간 동기화(WebSocket)를 통한 상태 전파
- WebRTC 영상 통화를 위한 시그널링 중계(WebSocket) 및 관련 STUN/TURN 접속 정보 제공
- 학습/테스트 중 웹캠 기반 실시간 인식·피드백(AI 서버와의 직접 통신)
- **펫(성장 요소) 관련 기능**: 펫 상태 조회 API, 경험치 증가·레벨업 처리 로직 — 데이터 구조(엔티티)만 준비하고 기능 구현은 후속 단계로 미룬다.
- **출석체크 관련 기능**: 출석 체크 API, 연속 출석일 계산 로직 — 데이터 구조(엔티티)만 준비하고 기능 구현은 후속 단계로 미룬다.
- **비정상(좀비) 방 강제 정리**: 실시간 연결(WebSocket)이 끊긴 것을 서버가 감지하지 못해(예: 서버 프로세스 재시작 등으로 연결 상태 자체가 유실되는 경우) 대기중/진행중 상태로 장시간 방치되는 방을 강제 정리하는 로직. REST 전용인 1차 범위에는 서버가 계속 붙들고 있어야 하는 연결 상태가 없어 이런 유실이 발생하지 않으므로, WebSocket 기반 실시간 기능이 도입되는 시점에 함께 추가한다.

### Key Entities *(include if feature involves data)*

- **사용자(User)**: 이메일, 비밀번호, 닉네임, 프로필 이미지, 누적 승/패 수, 탈퇴 여부(소프트 삭제) 등을 가진 서비스 이용자.
- **재발급 토큰(Refresh Token)**: 사용자별로 발급되어 인증 토큰 갱신에 사용되며, 로그아웃/탈퇴 시 무효화되는 자격 증명.
- **학습 콘텐츠(Sign)**: 카테고리(자음/모음/숫자/단어)별 학습 대상 항목으로, 노출 여부(활성 상태)를 가진다.
- **오답 기록(Wrong Answer Log)**: 사용자가 특정 학습 콘텐츠에서 오답을 신고한 이력.
- **게임방(Game Room)**: 참가 코드, 방장, 상태(대기/진행중/종료), 가장 최근 상태 변경 시각을 가지며 매칭 용도로만 사용되는 임시 리소스.
- **게임 결과(Game Session)**: 두 참가자, 각자의 점수, 승자, 시작/종료 시각을 기록하며 방과 독립적으로 영구 보존되는 매치 기록.
- **출석 기록(Attendance)**: 사용자별 출석 날짜와 연속 출석 일수를 담는 데이터 구조. *(1차 범위: 엔티티만 존재, API/로직 없음)*
- **사용자 펫(User Pet)**: 사용자 1인당 하나씩 보유하는 성장 요소로, 이름·레벨·경험치를 담는 데이터 구조. *(1차 범위: 엔티티만 존재, API/로직 없음)*

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 다른 도메인 API 구현이 시작되기 전에 API 문서화 체계가 먼저 준비되어, 이후 추가되는 모든 API 엔드포인트의 100%가 별도 수작업 없이 문서에 반영된다.
- **SC-002**: 신규 사용자가 회원가입부터 로그인, 프로필 확인까지 별도 안내 없이 3분 이내에 완료할 수 있다.
- **SC-003**: 정의된 회원/학습/테스트/게임방/랭킹 CRUD 기능 항목(펫·출석 제외)이 100% 구현되어 각 기능의 인수 시나리오를 통과한다.
- **SC-004**: 게임방 생성부터 결과 저장까지의 흐름에서 결과 데이터 유실 없이 100건 연속 테스트를 통과한다(중복 보고 포함).
- **SC-005**: 탈퇴한 사용자의 게임 전적·랭킹 관련 데이터는 탈퇴 이후에도 100% 보존되며, 탈퇴 계정으로의 로그인 시도는 100% 차단된다.
- **SC-006**: 랭킹 조회 결과의 상위 5명 순서가 실제 저장된 승/패 데이터와 항상 일치한다(정합성 100%).

## Assumptions

- 이번 1차 목표는 REST 기반 CRUD API 구현에 한정하며, WebSocket/SSE로 처리되던 실시간 목록 갱신, 게임 중 실시간 동기화, WebRTC 시그널링은 이후 단계에서 별도로 다룬다(`backend/jira-crud-backlog.md` 및 그 안의 API 명세 초안 기준으로 이미 제외됨).
- API 문서화(참고 자료의 `DOC-01-03`, Swagger 등)는 원래 참고용 부가 작업으로 백로그에 표기되어 있었으나, 이번 1차 개발에서는 다른 모든 도메인 기능보다 먼저 진행하기로 결정했다. 이에 따라 최우선 순위(P1) 사용자 스토리로 반영했다.
- 펫(user_pets)과 출석체크(attendance)는 데이터 구조(엔티티)만 미리 준비해 두고, 실제 API·경험치 증가·레벨업·출석 체크 로직은 이번 1차 범위에서 제외한다. 테스트 결과 보고, 게임 결과 저장 등 다른 기능은 펫 경험치 반영 로직 없이도 독립적으로 완결되도록 설계한다.
- 인증 방식은 기존에 문서화된 대로 JWT 기반 Bearer 토큰 + DB 화이트리스트(재발급 토큰) 방식을 그대로 따른다.
- 게임방은 1:1 전용이며, 3인 이상 매칭은 이번 범위에 포함되지 않는다.
- 오답노트는 오답 비율 계산 없이, 카테고리별 최근 5개 오답 이벤트를 그대로 보여주는 방식으로 충분하다(기존 결정 사항 유지).
